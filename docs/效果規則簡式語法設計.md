# 效果規則簡式語法設計

狀態：探索草案；只評估 parser 層可行性與適用範圍，不包含實作或設定遷移。

## 結論

可行，而且不需要改變 `EffectRule`、runtime、validator、描述器或內容指紋的語意。

建議新增一層**作者用簡式語法**：parser 先把「時機＋具名動作／封閉意圖巨集」正規化成既有 typed `EffectRule`，再走目前唯一的 validator、描述與 runtime。簡式不是另一套效果模型，也不新增武功專用 action。

不建議建立可自訂參數的通用 template／macro 系統。那會讓設定檔同時承擔繼承、展開、變數替換及錯誤追蹤，最後形成比目前 canonical schema 更難理解的第二套語言。本文件所稱「封閉意圖巨集」是 parser 內建、名稱與欄位皆封閉、只能機械展開成既有 action 的少數捷徑；作者不能自行宣告巨集、變數，巨集 payload 也不能引用另一個巨集。

## 現況量化

目前四份正式效果設定共有 424 條規則：

| 設定 | 規則 | 單一頂層動作 |
|---|---:|---:|
| `chess_combos.yaml` | 203 | 192 |
| `chess_equipment.yaml` | 116 | 116 |
| `chess_neigong.yaml` | 25 | 25 |
| `chess_magic_effects.yaml` | 80 | 66 |
| 合計 | 424 | 399（94.1%） |

其中 288 條（67.9%）落在下列十個非重疊的常見族群：

| 常見族群 | 規則數 |
|---|---:|
| 開場單一屬性修正 | 166 |
| 開場單一傷害修正 | 20 |
| 傷害後單一資源變更 | 21 |
| 命中單一狀態 | 11 |
| 命中單一傷害修正 | 33 |
| 定期單一資源變更 | 7 |
| 施放規劃單一修改 | 13 |
| 提交時單一攻擊修改 | 10 |
| 死亡單一效果傷害 | 3 |
| 主彈命中單一強制移動 | 4 |

這表示問題主要不是 canonical 抽象錯誤，而是作者必須反覆寫出事件、預設目標、單元素動作列表、動作型別及常見條件的完整結構。

目前 parser 其實已支援兩項基礎簡化：未填 `目標` 時預設為自身，固定整數 `EffectNumber` 可直接寫 scalar。但現有 424 條規則中有 312 條仍明寫 `目標: 自身`，沒有任何規則使用目標省略。單純刪除這 312 行已可減少篇幅，但「因為沒寫所以是自身」對新作者不夠直觀；`時機` 捷徑把預設目標變成具名且可查表的契約，較適合作為正式作者語法。

## 設計原則

1. 簡式與長式都只產生既有 `EffectRule`；正規化完成後不保留「簡式 runtime」狀態。
2. 一條簡式只能產生一條 canonical rule，避免改變 rule ID、觸發次數、冷卻、順序及來源歸屬；封閉意圖巨集可以在該 rule 內依序產生多個 canonical action。
3. 同一規則不可混用 `時機` 與 canonical `事件`，也不可同時使用提升後的單一 action node 與 `動作` 列表。
4. parser 只接受封閉的簡式名稱及欄位；未知欄位直接失敗，不做猜測或忽略。
5. 只隱藏穩定、不具爭議的 wiring。傷害階段、傳播政策、狀態合併、來源死亡及多 cast 生命週期等會改變語意的欄位不得憑武功名稱推斷。
6. 長式是複雜規則的正式表達方式，不是等待移除的舊格式；簡式是同一 schema 的作者介面。
7. 自動描述及內容指紋一律讀取正規化後的 typed rule；同語意的長式與簡式必須產生相同描述、相同內容指紋及相同 runtime。

## 簡式規則欄位契約

簡式規則只允許下列 rule-level 欄位：

| 欄位 | 必填 | 語意 |
|---|---|---|
| `時機` | 是 | 選擇固定的事件、預設目標及自動條件組合 |
| `目標` | 否 | 明確覆寫該時機的預設目標 |
| `條件` | 否 | 依作者順序追加在時機自動條件之後 |
| `機率` | 否 | 與 canonical rule 相同 |
| `次數` | 否 | 與 canonical `maxActivations` 相同 |
| `同來源冷卻幀數` | 否 | 與 canonical rule 相同 |
| `間隔幀數` | `時機: 每隔` 時必填 | 與 canonical rule 相同 |
| `每N次事件` | 否 | 與 canonical rule 相同 |
| `觸發限制` | 否 | 與 canonical rule 相同 |
| 一個提升後的具名動作／封閉意圖巨集 | 與 `動作` 二選一 | 單一作者 action node；巨集正規化後可產生多個 canonical action |
| `動作` | 與提升動作二選一 | 複合 action 列表；項目可為長式、具名 action 或封閉意圖巨集 |

`觀察範圍` 與 `施放匹配` 不屬於第一版簡式欄位；需要這兩種進階 wiring 時必須使用長式。rule control 仍全部交給既有 validator 判斷合法組合，不因使用簡式而放寬。現有 288 條候選規則中有 19 條使用至少一個 rule control，因此這些欄位是簡式覆蓋範圍的一部分，不是日後再補的選配。

## 第一層：常用時機

簡式以 `時機` 取代 `事件`，並提供最常見的目標及條件 wiring。作者仍可在允許的簡式中明確覆寫 `目標`，或追加條件；需要 `觀察範圍`、`施放匹配` 等進階 wiring 時改用長式。

| `時機` | canonical event | 預設目標 | 自動加入條件 |
|---|---|---|---|
| `開場` | `BattleInitialized` | 自身 | 無 |
| `每隔` | `FrameAdvanced` | 自身 | 無；必填 `間隔幀數` |
| `施放規劃` | `CastPlanned` | 自身 | 無 |
| `攻擊提交` | `AttackCommitted` | 自身 | 無 |
| `絕招施放` | `UltimateCommitted` | 自身 | 無 |
| `主彈命中` | `MainProjectileBeforeDamage` | 命中目標 | 無 |
| `命中` | `HitBeforeDamage` | 命中目標 | 無 |
| `傷害後` | `DamageResolved` | 自身 | 無 |
| `造成傷害後` | `DamageResolved` | 自身 | 傷害方位＝造成、已接受命中 |
| `受傷後` | `DamageResolved` | 自身 | 傷害方位＝承受、已接受命中 |
| `擊殺後` | `DamageResolved` | 自身 | 傷害方位＝造成、傷害造成死亡 |

`傷害後` 是原始事件捷徑；`造成傷害後／受傷後／擊殺後` 才是帶固定條件的意圖捷徑。兩者不能含糊互換。

時機表只定義正規化結果，不代表每個 loader 都允許所有結果。正規化後仍執行既有來源限制；例如 `chess_magic_effects.yaml` 不接受 `BattleInitialized`，因此其中的 `時機: 開場` 必須以指向原簡式規則的明確錯誤拒絕。其他 loader-specific 限制也不在簡式層複製一份平行矩陣。

自動條件永遠先於作者條件；作者條件保持 YAML 順序。若作者條件與自動條件具有相同 condition variant，載入失敗，不做去重或合併。例如 `時機: 造成傷害後` 已加入一般「已接受命中」；若需要 `需要正傷害: true`，作者必須改用 `時機: 傷害後`，明確寫出「傷害方位」及自訂「已接受命中」。這可避免重複描述及隱含的條件強化規則。

未來若遷移既有設定，converter 必須永遠保留明寫的 `目標`。canonical `事件: 命中傷害前` 未寫目標時代表自身，而 `時機: 命中` 的預設是命中目標；遇到省略目標的 canonical 規則時，converter 必須在簡式中明寫 `目標: 自身`，不得機械刪除後造成靜默語意翻轉。現有正式設定全部明寫目標，但這仍是格式轉換契約。

## 第二層：動作提升與封閉意圖巨集

目前 94.1% 規則只有一個頂層動作。簡式可把唯一作者 action node 提升成規則的具名欄位，省略單元素 `動作` 列表及 `類型`：

```yaml
# canonical
- 事件: 戰鬥初始化
  目標: 自身
  動作:
    - 類型: 屬性修正
      屬性: 防禦
      方式: 固定加算
      數值: 50

# 簡式
- 時機: 開場
  屬性修正:
    屬性: 防禦
    方式: 固定加算
    數值: 50
```

一條簡式規則必須恰有一個提升 action node；該 node 若為封閉意圖巨集，正規化後可以展開成多個 canonical action。複合規則保留 `動作` 列表，但列表項目也可使用相同的具名動作或巨集形式：

```yaml
- 時機: 主彈命中
  動作:
    - 擊退:
        距離格數: 4
    - 傷害修正:
        方位: 造成
        階段: 最終
        傷害種類: 全部
        方式: 百分比加算
        數值: -20
        持續幀數: 90
        合併方式: 刷新
```

這種形式只移除結構噪音；第二個動作仍明確保留方位、階段及正負號，不假設「降低傷害」必然發生在哪一個結算階段。

## 建議的第一批具名動作與封閉意圖巨集

| `屬性加成` | 一至多個 `ModifyAttribute` | 以 `固定／百分比` 屬性表展開；共用持續與疊加欄位 | 很高；目前有 211 個 scalar 固定／百分比屬性 action |
| `回復資源` | `ChangeResource(Restore)` | `方式: 回復` | 高；命中、擊殺、定期與施放回復共用 |
| `獲得資源` | `ChangeResource(Grant)` | `方式: 獲得` | 中；護盾、狀態護盾及幀數資源 |

| `拉近` | `ForceMove(TowardSource)` | 方向、阻擋前停止、受阻縮短 | 低至中；目前 1 個，但意圖清楚且與擊退成對 |
| `移除狀態` | `RemoveStatus` | 只省略 action wrapper | 中 |

### 封閉意圖巨集：屬性加成

`屬性加成` 解決「同一時機、目標、期限及疊加政策下，重複加入多個 scalar 屬性」的高頻情況：

```yaml
- 時機: 開場
  屬性加成:
    固定:
      攻擊: 50
      防禦: 30
    百分比:
      速度: 15
      暴擊率: 10
```

它在同一條 canonical rule 內展開成四個 `ModifyAttributeAction`：`固定` 對應 `方式: 固定加算`，`百分比` 對應 `方式: 百分比加算`，內層數字成為 `數值`。兩種表都接受有正負號的 scalar 常數，因此減益可直接寫負值；`百分比` 是 attribute operation，不是 `EffectNumber` 的基準百分比公式。

限時共用加成寫法如下：

```yaml
- 時機: 絕招施放
  屬性加成:
    百分比:
      攻擊: 30
      防禦: 30
      速度: 30
    持續幀數: 100
    合併方式: 刷新
```

`持續幀數／合併方式／層數上限／每層／疊加範圍` 逐一複製到所有生成 action；未填時各 action 使用既有 canonical 預設。巨集的封閉契約如下：

- `固定` 與 `百分比` 至少有一個，存在時必須是非空 map；除此之外只接受上述五個共用欄位。
- map key 必須是現有 canonical 屬性名稱，value 必須是 scalar 數字；公式值、覆寫、乘算與至少為仍使用 `屬性修正`。
- 同一屬性不可同時出現在兩個 operation map；需要同時固定及百分比修改時，作者必須在 `動作` 中明寫兩個 `屬性修正`，讓順序與意圖可見。
- 展開順序固定為 `固定` 後 `百分比`，各 map 內依唯一的 canonical `BattleAttribute` 順序；不得依賴 YAML map 的輸入或容器迭代順序。
- 巨集只展開 action，不可展開成多條 rule；rule-level 機率、條件、每 N 次、次數及冷卻只評估一次。
- 若各屬性需要不同期限、疊加政策或數值公式，改用一般 `動作` 列表；不增加 `全屬性／攻防速` 等會隱藏成員集合的虛擬屬性。

`屬性加成` 可作為提升後的唯一 action node，也可放在任何 action 列表中；在列表中展開時占據原 node 的位置。條件分支等巢狀 action 列表也使用同一展開規則，不建立第二套巨集範圍。

### 封閉意圖巨集：常用資源

最常見、資源與方式都固定的三種資源變更可直接寫意圖名稱：

```yaml
回復內力: 30

回復生命:
  數值:
    目標最大生命百分比: 8
  治療種類: 擊殺獎勵

獲得護盾:
  每星級: 100
```

`回復內力` 與 `獲得護盾` 的 value 就是完整 `EffectNumber` node，可為 scalar、canonical number 或第三層列出的單基準別名，不另包一層 `數值`。它們分別固定展開成 `Mp + Restore` 與 `Shield + Grant`，不接受治療、轉移或其他資源欄位。

`回復生命` 接受兩種互斥形狀：scalar／`EffectNumber` node 直接代表數值，並使用 canonical `直接／來源必須存活` 預設；需要 metadata 時改用含必填 `數值`、選填 `治療種類／來源政策` 的 payload map。map 只要出現這三個 payload key 的任一個，就必須按 payload 形狀解析並拒絕其他外層欄位；否則整個 value 按 `EffectNumber` 解析。payload map 不能同時在外層混寫 `EffectNumber` 欄位。`治療種類` 不可由 `時機` 猜測，例如命中時使用 scalar 仍是直接治療；作者要分類為命中治療就必須明寫。兩種形狀都固定展開成 `Hp + Restore`，仍走既有治療交易，不直接改寫生命。

其他資源、奪取、移除、轉移及至少刷新至仍使用 `回復資源／獲得資源／奪取資源` 或 canonical `資源變更`；不為每個 enum 組合自動產生名稱。

### 封閉意圖巨集：固定傷害 wiring

`忽略防禦` 與 `單次承傷上限` 都直接接受一個 `EffectNumber`：

```yaml
忽略防禦: 30

單次承傷上限: 20
```

- `忽略防禦: V` 固定展開為 `方位: 造成／階段: 防禦前／傷害種類: 招式／方式: 忽略防禦百分比／數值: V`。
- `單次承傷上限: V` 固定展開為 `方位: 承受／階段: 最終／傷害種類: 全部／方式: 單次承傷上限／數值: V`。

兩者不接受期限或疊加欄位；需要改變方位、階段、傷害種類或持續政策時必須使用 `傷害修正`。一般「增加／降低傷害」不建立意圖巨集，因為方位與結算階段不是可安全隱藏的固定 wiring。

`擊退／拉近` 只能在目前所有既有使用都一致的碰撞政策下省略欄位。若未來需要穿越、交換位置或受阻時產生其他後果，必須回到 `強制移動` 長式，不能悄悄改變捷徑定義。

距離單位會改變 runtime 類別，必須在簡式契約中明確區分：

- `距離格數` 是 ordinary action，可以出現在複合 `動作` 列表。
- `距離像素` 是 exact-runtime action，支援 `鎖定幀數`，但必須是該規則唯一 action。
- 像素移動可使用 rule-level `機率`，由 exact consumer 直接消耗；不可使用 `每N次事件`、`觸發限制`、`次數` 或 `同來源冷卻幀數`，也不可與一般動作混合。
- 簡式 parser 應針對上述違規回報「像素擊退／拉近屬於精確階段」的作者級錯誤，而不是只暴露一般 validator 的混合動作訊息。

## 第三層：常見數值公式

固定整數目前已可直接寫成 scalar，應保留：

```yaml
數值: 30
```

真正不友善的是簡單比例與星級公式仍要寫 `基準／百分比`，且「每星級 100」目前會出現 `百分比: 10000`。建議只為高頻、單一基準公式提供封閉別名：

```yaml
數值:
  目標最大生命百分比: 3

強度:
  每星級: 100

數值:
  實際生命傷害百分比: 50

數值:
  目標目前護盾百分比: 20
  取整: 向零
```

精確展開如下：

| 簡式 | canonical `EffectNumber` |
|---|---|
| `目標最大生命百分比: P` | 基準＝目標最大生命、百分比＝P |
| `來源最大生命百分比: P` | 基準＝來源最大生命、百分比＝P |
| `目標目前生命百分比: P` | 基準＝目標目前生命、百分比＝P |
| `目標目前護盾百分比: P` | 基準＝目標目前護盾、百分比＝P |
| `實際生命傷害百分比: P` | 基準＝實際生命傷害、百分比＝P |
| `每星級: N` | 基準＝來源星級、百分比＝N×100 |

多基準乘算、狀態槽、累計值、上下限及特殊取整仍使用 canonical number。不要加入可解析字串算式，例如 `"攻擊×已損血 45%"`；它難以做欄位級診斷，也會變成另一個運算式語言。

## 第四層：條件簡寫

無參數條件可接受 scalar；單參數條件可接受單鍵 map：

```yaml
條件:
  - 已接受命中
  - 傷害來自招式
  - 自身生命低於: 30
```

正規化後分別等同：

```yaml
條件:
  - 類型: 已接受命中
  - 類型: 傷害來自招式
  - 類型: 自身生命低於
    百分比: 30
```

帶兩個以上參數的條件，例如需要正傷害且排除反彈的「已接受命中」，保留長式，避免同一 scalar 名稱暗藏多組預設。

無參數條件只能使用 scalar；`僅限絕招: true` 之類帶值寫法必須拒絕，並提示改寫為 `- 僅限絕招`。單鍵 map 只供該條件 canonical schema 恰有一個參數的情況使用，不能把多參數 condition 的其中一部分藏成預設。

## 完整簡式例子

### 主彈命中套用寒毒

```yaml
- 時機: 主彈命中
  套用狀態:
    狀態: 寒毒
    持續幀數: 90
    強度: 25
    合併方式: 刷新
```

正規化為 `MainProjectileBeforeDamage／HitTarget／ApplyStatus`，其餘欄位仍交給既有 status validator。

### 命中回復內力

```yaml
- 時機: 造成傷害後
  回復內力: 30
```

正規化為 `DamageResolved`，加入「造成＋已接受命中」，目標為自身，action 為 `ChangeResource(MP, Restore, 30)`。

### 擊殺回復生命

```yaml
- 時機: 擊殺後
  回復生命:
    數值:
      目標最大生命百分比: 8
    治療種類: 擊殺獎勵
```

### 定期生命回復

```yaml
- 時機: 每隔
  間隔幀數: 80
  回復生命:
    數值:
      目標最大生命百分比: 3
    治療種類: 生命回復
```

## 不應簡化的範圍

下列內容即使看起來冗長，也不適合以高階意圖隱藏：

- 22 個狀態機 action：最大傷害記錄、傷害吸收、規則借用、攻擊複製、分身、死亡庇護及挪移次數都牽涉跨事件狀態與生命週期。
- 3 個條件分支：成立／否則的 action 順序是效果本身，不應壓成單一名稱。
- 2 個持續區域：geometry、anchor、來源死亡及 merge policy 都是必要語意。
- 攻擊複製、延遲攻擊、多彈道及 child cast 的傳播政策：省略會重新引入 provenance／compatibility 問題。
- 七星、太極、柔雲等跨規則狀態配對：一個 shortcut 不可展開成多條 rule。
- 依狀態名稱猜層數、強度、持續時間或合併方式：同一狀態在不同來源可能需要不同政策。
- `眩暈／中毒／無敵` 等狀態專名巨集：只少寫一個 `狀態` 欄位，卻會為每個狀態建立平行 vocabulary；第一批仍使用 `套用狀態`。
- 依武功名稱建立 `黯然公式／打狗效果` 等特例：這等同重新建立以技能命名的舊 `EffectType`。

這些規則仍可使用 action wrapper 或條件 scalar 等局部簡寫，但核心 wiring 應保持可見。

## Parser 邊界與驗證

若未來實作，建議流程為：

```text
YAML 長式或簡式
    → 作者語法解析與嚴格欄位檢查
    → 正規化為 EffectRule
    → 現有 validateEffectRule
    → 現有描述器／內容指紋／runtime
```

不建議把整條簡式生成人工 YAML rule 再從頭解析，因為會弱化原始行列資訊。rule-level `時機／目標／控制欄位` 應直接填入 typed draft；具名 action 與條件簡寫則應機械補上 canonical `類型` 後重用既有 action／condition parser，避免維護第二份 payload 欄位解析。封閉意圖巨集只負責驗證自己的封閉外形、補入固定欄位並呼叫 canonical action／`EffectNumber`／stack parser。錯誤訊息仍引用原始簡式規則及欄位，最後交給同一 `validateEffectRule`。

具名 action dispatch 規則如下：

- 沒有 canonical `類型` 的 action map 必須恰有一個已知具名 action key。
- key 與 canonical label 同名沒有歧義；例如 `套用狀態` 的內層 payload 仍由同一 `ApplyStatusAction` parser 處理。
- 未知單鍵 action 回報 `未知簡式動作「名稱」`；零個或多個 action key 回報簡式 action 形狀錯誤。
- 長式 action、具名 action 及提升後的單一 action node 可在不同規則中並存，但同一 action node 不能混寫兩種形式。
- action-list parser 的正規化結果是 action sequence，不再假設每個作者 node 恰好回傳一個 action；一般長式／具名 action 回傳一個，`屬性加成` 依固定順序回傳多個，並在原位置插入。
- promoted 巨集雖可回傳多個 action，仍只建立一條 rule、使用一個 rule ID 及一份 rule control 狀態；不得以「每個展開 action 建一條 rule」實作。

必要驗證契約：

- 每個簡式各有長式對照，逐項斷言該簡式會設定的 normalized event、selector、condition、rule control 及 action payload 欄位相等。
- 不要求為全部 `EffectRule` 與約四十個巢狀 variant 新增 production `operator==`；具名 action／condition 必須重用 canonical parser，使未改寫的 payload 欄位由同一程式路徑產生。
- 完整／精簡描述及內容指紋必須相等，但兩者是第二層回歸證據，不能取代欄位級對照。現有內容指紋的 structured view 並未獨立列出所有 selector、every-N 與 activation-limit 欄位，部分語意只透過描述文字進入指紋。
- rule ID 仍只由來源與作者規則序號決定。
- `屬性加成` 必須對照生成 action 的數量、canonical 順序、operation、數值及每個共用持續／疊加欄位；並斷言多個 action 仍只產生一條 rule。
- 資源與固定傷害巨集必須分別覆蓋 scalar、合法 formula／payload、canonical 預設及固定 wiring；空表、重複屬性、formula 屬性值、混合生命 payload、未知欄位及巨集 shape 錯誤均需有失敗測試。
- 簡式未知欄位、長短式混用、兩個提升 action node、不合法時機／動作組合、重複自動條件、未知具名 action 及無參數條件帶值均載入失敗。
- exact-runtime action 仍受目前的機率、every-N、觸發限制及一般動作混用限制。
- 修改任何簡式固定展開語意都視為內容語意變更，必須更新對照測試及內容指紋。

## 可行性與建議範圍

技術可行性高，runtime 風險低；主要風險在 parser 診斷、預設值是否過度，以及簡式目錄日後膨脹。

建議第一批只納入：

1. `時機` 捷徑與 contextual 預設目標。
2. 單一 action node 提升，以及複合／巢狀 `動作` 列表內的具名 action 與封閉意圖巨集。
3. `屬性修正／回復資源／獲得資源／奪取資源／套用狀態／擊退／拉近` 等具名 action。
4. `屬性加成／回復內力／回復生命／獲得護盾／忽略防禦／單次承傷上限` 六個封閉意圖巨集。
5. 六個高頻單基準數值別名。
6. 無參數與單參數條件簡寫。

這一批可直接涵蓋目前最重複的 288／424 條規則；依建議的安全 action 集合計算，ultimate 設定中 47／80 條可使用完整簡式，其餘規則仍能使用局部簡寫。

新增簡式的長期門檻建議為：至少已有三個使用點且跨兩個內容來源，或單次可移除至少五行純 wiring；必須能一對一正規化成既有 typed rule，且不得以技能名稱命名。`拉近` 可作為 `擊退` 的對稱例外，因為兩者共享同一 `ForceMove` 語意與驗證。
