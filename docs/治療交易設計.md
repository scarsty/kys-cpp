# 治療交易設計

## 目的

目前生命回復分散在隊伍效果、傷害交易、死亡效果與救援流程，且使用不同事件型別。寒毒、枯骨與血刀若各自在這些路徑加判斷，必然漏掉其中一條。

本設計建立一個共用的純計算 resolver 與一個 runtime commit 入口。它不把 MP、護盾或傷害交易一起塞進「萬用資源系統」，也不改變既有治療的取整與事件順序。

## 請求、修正與結果

```cpp
enum class BattleHealKind
{
    Direct,
    Team,
    Aura,
    OnHit,
    KillReward,
    DeathMedical,
    Rescue,
    Regeneration,
    Lifesteal,
};

enum class BattleHealBase
{
    TargetMaxHp,
    FinalHpDamage,
    PrecomputedLegacyAmount,
};

struct BattleHealAmount
{
    BattleHealBase base{};
    int baseValue{};        // FinalHpDamage／legacy amount；TargetMaxHp 時由目標快照取得
    int flat = 0;
    int percent = 0;
    BattleHealRounding rounding{};
    int minimum = 0;
};

struct BattleHealRequest
{
    HealTransactionId id{};
    int sourceUnitId{};
    int targetUnitId{};
    EffectSourceBinding source{};
    std::optional<BattleCastId> castId;
    BattleHealKind kind{};
    BattleHealAmount amount{};
    BattleHealSourcePolicy sourcePolicy{};
};

struct BattleHealModifierState
{
    bool blocked = false;
    int receivedHealPct = 100;
};

enum class BattleHealOutcome
{
    Applied,
    Blocked,
    AlreadyFull,
    ZeroAfterModifier,
    IneligibleSource,
    IneligibleTarget,
};

struct BattleHealResult
{
    BattleHealRequest request{};
    BattleHealOutcome outcome{};
    int calculatedAmount{};
    int modifiedAmount{};
    int hpBefore{};
    int hpAfter{};
    int appliedAmount{};
};
```

`sourcePolicy` 只有兩種合法值：一般治療要求來源存活；死亡醫療明確允許死亡來源。同步呼叫在函式邊界要求目標存活；真正可能跨命令佇列的請求若在 commit 前失去合資格來源／目標，回傳 `IneligibleSource／IneligibleTarget`。治療不隱含復活。

## 唯一計算順序

```text
驗證 source／target 與 request
→ 依 BattleHealAmount 計算 requested amount
→ 目標已滿血則以 AlreadyFull 結束
→ 發出內部 HealAttempted 快照
→ 收集目標在該時點的治療 modifier
→ 寒毒等完整阻止
→ 依順序套用 received-heal 百分比並取整
→ clamp 到 [目前 HP, 最大 HP]
→ 寫入 HP
→ appliedAmount > 0 時發出 HealApplied
```

數值計算固定為：

1. `base × percent / 100` 使用 payload 指定取整。
2. 加上 `flat`。
3. 若原始計算為正，套用 `minimum`。
4. 依 effect source ordering 套用治療修正；枯骨的 75%降低即 `receivedHealPct = 25`。
5. 每次乘算依 modifier schema 指定取整；第一版使用向零取整，並以測試鎖定。
6. 最後才按缺失生命 clamp。

寒毒將 `blocked` 設為 true，阻止直接治療、吸血、生命回復、命中回血、擊殺回血、死亡醫療與救援；不影響護盾、MP 或復活。枯骨只修改正治療量，不把治療反轉成傷害。

## `HealAttempted` 與 `HealApplied`

- `HealAttempted` 是交易內部 hook，攜帶尚未修改的 calculated amount。寒毒／枯骨在此提供 modifier，不直接改 HP。
- `HealApplied` 只在 `appliedAmount > 0` 時發出，與目前滿血不產生 heal event 的行為一致。
- 已滿血的合法請求在 modifier hook 前即得到 `AlreadyFull`；可以被測試觀察，但不產生 `HealAttempted`、presentation、音效或「受到治療後」proc。
- 被寒毒阻止的請求為 `Blocked`；可產生具名狀態 log，但不冒充 0 點治療。
- 一個 transaction ID 最多產生一次 applied event，重複 commit 直接 assert。

效果 schema 第一版只允許治療 modifier 讀取 `HealAttempted`；一般「受到治療後」效果只能訂閱 `HealApplied`，避免滿血時因新的內部 attempt hook 偷偷觸發舊行為。

## 純 resolver 與 runtime facade

```cpp
BattleHealResult resolveHeal(
    const BattleHealRequest& request,
    const BattleHealUnitSnapshot& source,
    const BattleHealUnitSnapshot& target,
    const BattleHealModifierState& modifiers);

BattleHealResult BattleHealSystem::commit(
    BattleRuntimeState& state,
    const BattleHealRequest& request);
```

傷害系統可以在自己的 snapshot transaction 中呼叫同一個 `resolveHeal`，再把結果寫回 attacker snapshot；隊伍、死亡與救援流程使用 `BattleHealSystem::commit`。兩者共用完整演算法與事件轉換，不複製 clamp／modifier 邏輯。

這個分層保留 `BattleDamageSystem::resolveTransaction` 的原子性；不能為追求單一 facade 而把擊殺回復挪到另一幀。

## 現有路徑遷移表

| 現有路徑 | request | 既有數值／取整 | 必須保留的順序與特殊行為 |
|---|---|---|---|
| `BattleTeamEffectSystem::applySelfHeal` | `Direct` | `maxHp × pct / 100`，整數向零 | 滿血無 applied event |
| `applyTeamHeal` | `Team` | `flat + maxHp × pct / 100`，整數向零 | 依 `units.live()` 現有順序逐人；滿血不報 event |
| `applyLowestAllyHeal` | `Team` | 同上 | selector 先排除滿血；生命比例平手以 unit ID |
| `applyHealAura` | `Aura` | 同上 | 不治療來源自己；半徑判定與迭代順序不變 |
| `BattleDamageSystem::applyKillReward` | `KillReward` | `maxHp × killHealPct / 100`，整數向零 | 死亡確認後立即在 damage transaction 內結算，早於 on-hit 回血 |
| `applyOnHitResources` 的 HP | `OnHit` | 固定 `hpOnHit` | 只在 accepted hit；在 kill reward 後；MP drain／restore 相對順序不變 |
| `BattleDeathEffectStore::DeathMedical` | `DeathMedical` | `max(1, maxHp × pct / 100)` | 來源已死亡仍合法；依現有 ally／effect 迭代順序 |
| `BattleRescueRepositionSystem` | `Rescue` | `max(1, maxHp × ProtectionHealPct / 100)` | 原本預算與 clamp 改由 resolver 執行；位移、治療、無敵的 commit 順序不變 |

治療光環目前即使目標滿血，仍可能執行「光環內冷卻縮減」，因為 cooldown 分支不依賴實際回血。遷移時冷卻縮減保留為同一 aura evaluation 內的獨立 action，不能簡化成 `HealApplied` 後才觸發。

`KillRewardApplied` 目前同時代表治療、無敵與加攻。遷移後拆成具型別結果，但 presentation adapter 維持原事件相對順序；不能因拆型別改變 battle log 或 digest。

## 血刀吸血

血刀大法使用 damage transaction 的 `finalHpDamage`，不使用原始傷害、護盾吸收或過量處決值：

```cpp
BattleHealRequest{
    .sourceUnitId = attackerId,
    .targetUnitId = attackerId,
    .kind = BattleHealKind::Lifesteal,
    .amount = {
        .base = BattleHealBase::FinalHpDamage,
        .baseValue = damageResult.finalHpDamage,
        .percent = 50,
        .rounding = BattleHealRounding::TowardZero,
    },
};
```

- `finalHpDamage == 0` 不建立請求。
- 同一絕招多次命中，每筆 damage result 各自吸血並各自取整；不先合計再乘 50%。
- 擊殺時先保留現有 kill reward 與 on-hit resource 順序，damage transaction 完成後的 `DamageResolved` 才提交血刀吸血。
- 施法者在此時已死亡則依一般 source policy 不套用。
- 吸血受寒毒完整阻止，受枯骨治療降低；不受「造成傷害增加」再次放大。

## 來源死亡與死亡連鎖

- 死亡醫療的 `sourceUnitId` 是死者，`sourcePolicy` 明確允許死亡來源；target 必須存活。
- 普通治療若來源在 request 產生後、commit 前死亡，不套用。同步 transaction 中以 transaction snapshot 的明確時間點判斷。
- 目標在 commit 前死亡不套用，也不復活；若需要復活，必須是另一個具型別系統。
- 乾坤反彈、蛤蟆毒爆造成的傷害若觸發其他死亡效果，治療事件按 frame runner 原有死亡序列插入，不能批次到幀末一起處理。

## 事件與 presentation 整併

正式 runtime 最終只保留：

```cpp
enum class BattleHealEventType { Attempted, Applied, Blocked };
```

與效果 schema 的名稱及映射固定如下：

| 治療交易事件 | `EffectEvent` | 是否可被一般規則訂閱 |
|---|---|---|
| `BattleHealEventType::Attempted` | `EffectEvent::HealAttempted` | 只允許治療 modifier |
| `BattleHealEventType::Applied` | `EffectEvent::HealApplied` | 是，代表實際回復量大於 0 |
| `BattleHealEventType::Blocked` | 無 | 第一版只供狀態 log／presentation，不進效果 dispatcher |

不存在 `HealResolved` 這個 schema 名稱。若未來確實需要訂閱失敗／零值結果，必須新增具體 outcome event 並補 payload capability，不能把 `Applied` 擴成含 0 的模糊「resolved」。

`Applied` 攜帶 heal kind、來源 binding、before／after／amount；log／visual adapter 依 kind 產生既有「擊殺回復」「死亡醫療」「保護挪移」等 semantic label。字面 label 不回流為 gameplay 判斷。

遷移期間可由 adapter 同時產生舊 presentation event 供 trace 差分，但正式切換後刪除 `BattleTeamEffectEvent::Heal`、`BattleDamageEvent::HpRestored` 中重複的治療資料及 `BattleDeathEffectEvent::DeathMedicalHeal`。

## 測試

### 舊行為等價

- 每條現有路徑測試 1 HP 缺口、部分缺血、滿血與百分比不能整除。
- kill reward、on-hit HP、MP drain／restore 與 status 的 event 順序 golden。
- death medical 的最少 1 點與死亡來源。
- rescue 的位移 → 治療 → 無敵／反擊相對順序。
- aura 滿血但仍縮短 cooldown 的負向防簡化測試。

### 新 modifier

- 寒毒逐一阻止九種 heal kind，不阻止護盾。
- 枯骨對固定、最大生命比例、混合值、最少值與吸血的取整。
- 寒毒＋枯骨同時存在時 blocked 優先，且不消耗額外亂數。
- full HP、zero after modifier、source dead、target dead 都不發 `HealApplied`。
- 血刀只讀 `finalHpDamage`，不含 shield absorbed 或 overkill，逐 hit 取整。

GUI／headless 必須得到相同的 event stream、HP runtime 與 fixed-seed digest。
