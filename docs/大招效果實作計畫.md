# 大招效果實作計畫（共用效果系統修訂版）

## 關鍵決定

在實作任何新絕招前，先把目前的 `ComboEffect` 整理成所有戰鬥效果來源共用的資料模型及執行管線。

- 羈絆、裝備、裝備羈絆、內功與絕招使用同一個 `EffectRule`、同一個 runtime store、同一組事件及同一個執行器。
- 不新增 `ChessUltimateEffects`、絕招專用 action hierarchy 或第二套 selected-skill effect state。
- YAML 不保存手寫機制說明。效果數值只在結構化規則中出現一次，完整／精簡描述都由同一份解析後資料自動產生。
- 不把每門武功或目前每個 `EffectType` 原樣搬成一個新 action。先拆出觸發、目標、條件、動作與數值算法，消除目前排列組合式的型別膨脹。
- 商店刷新、金幣、戰場選擇及「計作羈絆」不是戰鬥事件，從戰鬥效果模型移回各自的管理／配隊資料；它們仍使用自動描述，但不進入戰鬥 dispatcher。
- `config/chess_magic_effects.yaml` 在 59 招全部完成前維持停用；59 招與最終驗證現已完成，最後的獨立啟用變更已套用。

本計畫取代先前「共用事件骨架、另建絕招效果語言」的方向。

## 現有系統稽核

目前 `EffectType` 同時表示效果本身、作用目標、數值方式及部分觸發時機，因此已形成型別乘積：

- `FlatATK`、`PctATK`、`TeamFlatATK`、`TeamPctATK` 本質上都是「修改攻擊」，差別只是算法與目標。
- `HPOnHit`、`KillHealPct`、`OnSkillTeamHeal`、`LowestAllyHeal` 本質上都是「回復生命」，差別是事件、選擇器與數值。
- `OnSkillTeamHeal` 與 `OnSkillTeamHealPct` 只因固定值／百分比而成為兩個型別。
- `ArmorPenChance`、`ArmorPenPct`、`ArmorPen` 是同一機制歷次擴充留下的重疊表示。
- `OffensiveCharm` 載入後還會暗中展開成第二個 `CharmCDRDebuff`，設定看見的規則與 runtime 實際規則不一致。

目前設定規模：

| 來源 | 效果條目 | 不同類型名稱 |
|---|---:|---:|
| `chess_combos.yaml` | 212 | 95 |
| `chess_equipment.yaml` | 130 | 40 |
| `chess_neigong.yaml` | 25 | 22 |
| 當時停用的 `chess_magic_effects.yaml` | 92 | 17 |

C++ 目前有 453 處 `EffectType::` 引用，且解析、描述、初始化摘要、觸發白名單及實際結算分散在不同 switch／查詢中。若只為 59 招再加一組 action，確實會得到另一堆相似但不互通的效果。

`RoleComboState` 目前已是 `BattleEffectState` 的空 subclass，後者也已被武功效果重用；`BattleEffectSources` 與 `BattleComboTriggerSystem` 內的 reader／commands 也已有來源無關能力。runtime 底座大致存在。剩餘工作是沿用並演進這些型別、合併 normal／ultimate 武功 store、清理來源綁定與約 66 處舊命名，而不是另造一個 generic store 或重寫 reader／commands。

## 統一資料模型

### 一條規則

所有戰鬥效果都解析成同一種規則：

```cpp
struct EffectRule
{
    EffectEvent event{};
    EffectSelector selector{};
    std::vector<EffectCondition> conditions;
    int chancePct = 100;
    int maxActivations = 0;
    std::vector<EffectAction> actions;
};
```

- `EffectEvent`：何時評估，例如常駐、出手、絕招提交、主彈道命中傷害前、受傷後、護盾破裂、死亡。
- `EffectSelector`：作用於誰，例如自己、羈絆成員、全隊、命中目標、最低生命三人、半徑內敵人。
- `EffectCondition`：是否符合，例如僅限絕招、僅限主彈道、生命不高於 50%、另一名夫妻刀法使用者存活。
- `chancePct／maxActivations`：現有觸發機率及次數上限的共用欄位。
- `EffectAction`：真正做什麼。使用少量具型別 action family，不再用 `value/value2` 猜參數。

### 動作族群

第一輪只建立真實設定需要的族群：

具體 enum、payload struct、必要／預設欄位、event/action 合法矩陣與舊型別映射以[效果規則 Payload 設計](效果規則Payload設計.md)為準；下表只保留能力總覽，不作為 schema。

| 動作族群 | 參數例子 | 可取代的既有型別／新需求 |
|---|---|---|
| 屬性修正 | 屬性、固定／百分比、數值、持續、疊加 | Flat／Pct／Team 系列、暴擊、閃避、格擋、CDR、速度等 |
| 傷害修正 | 固定／百分比、傷害種類、忽略防禦、上限 | 固定加減傷、技能傷害、穿甲、減傷、枯骨、空明 |
| 資源變更／治療交易修正 | HP／MP／護盾、固定／最大值比例、轉移；阻止／受治療倍率 | 回血、回內、吸內、全隊回內、各種護盾、寒毒、枯骨 |
| 套用／移除狀態 | 狀態、強度、持續、層數、合併 | 中毒、流血、眩暈、封內、寒毒、刺目、七星、狀態盾 |
| 造成傷害 | 固定、每星、屬性倍率、傷害種類、範圍 | 死亡 AOE、龍象、金蛇、乾坤反彈、蛤蟆毒爆 |
| 修改／生成攻擊 | 數量、形狀、倍率、延遲、追蹤、命中組 | 追加彈、連鎖、五虎、太嶽、六脈、火焰、玉女 |
| 強制移動 | 方向、格數、地形／佔位規則 | 擊退、銀索拉近、既有救援位移 |
| 建立區域 | 形狀、半徑、持續、跟隨、區域修正 | 黃沙、伏魔陣 |
| 修改施放 | 內力消耗、射程／遠程化、免費追加 | 神照、混元、彈指、小無相 |
| 執行狀態機 | 記錄值、吸收值、複製政策 | 太極記憶、乾坤、小無相、斗轉、葵花 |

最後一列只放不能由前九列忠實組合的狀態機。它們以機制命名，不以武功命名，例如 `RecordMaximumSkillHpDamage`，讓太極拳、太極劍法及柔雲共用。新增單招專用狀態機時，必須在 code review 說明為何一般事件＋動作無法忠實表示。

### 來源不是另一套效果

每條解析後規則在進入戰鬥時加上來源綁定：

```cpp
struct EffectSourceBinding
{
    EffectSourceKind kind{}; // Combo, Equipment, EquipmentSynergy, Neigong, Magic
    int sourceId{};
    int ownerUnitId{};
    int sourceTeam{};
};
```

單位沿用並演進現有 `BattleEffectState`，最終只有一個來源無關的效果 store（是否同步更名為 `BattleEffectStore` 只屬命名清理）：

- 靜態定義：該單位從羈絆、裝備、內功及絕招取得的全部規則。
- 索引：按事件及常駐修正鍵建立，取代 `idsByTriggerAndType` 與 `sumAlways(EffectType)`。
- runtime：每條規則的啟用次數、計時、層數、逐目標層數及 pending 狀態。

絕招規則也在同一 store 中，只是條件要求事件內容的 `magicId` 相符且 `ultimate == true`。彈道攜帶 `castId／magicId／propagationPolicy`，不再攜帶指向另一個 skill effect store 的欄位。

因此可刪除：

- `BattleUnitMagicEffectRuntime::normal／ultimate` 兩個平行 store。
- `BattleEffectSources` 將 combo 與 skill 兩邊合併後再查詢的邏輯。
- selected-skill 專用的 `BattleEffectRuntimeRegistry` 白名單。
- `normalizedMagicEffects()` 這類載入後暗中複製效果的處理。

## 共用 YAML 與自動描述

### 同一種效果節點

羈絆、裝備及內功的 `效果`，與武功條目內的 `效果`，都使用同一份 parser。

羈絆中的常駐效果：

```yaml
效果:
  - 時機: 開場
    目標: 羈絆成員
    屬性修正:
      屬性: 防禦
      方式: 固定加算
      數值: 60
```

絕招效果：

```yaml
啟用: true

絕招:
  - 武功: 59
    名稱: 五虎斷門刀
    效果:
      - 時機: 施放規劃
        條件:
          - 僅限絕招
        修改攻擊:
          樣式: 扇形
          數量: 5
          傷害倍率: 60
          貫穿: true
          視為主彈道: true
          同目標命中上限: 1
      - 時機: 主彈命中
        目標: 命中目標
        套用狀態:
          狀態: 流血
          層數: 2
          持續幀數: 90
          合併方式: 刷新
```

設定沒有 `說明`，也不在字串中重複 5、60%、2 層或 90 幀。

### 描述產生

`effectDescription(rule, style)` 讀取事件、選擇器、條件及 action payload，自動產生完整或精簡描述。以上五虎規則可產生：

compound rule 不靠字串串接猜關係；多動作順序、同時動作、條件分支及跨事件狀態機依[效果描述語法設計](效果描述語法設計.md)先產生 semantic AST，再由完整／精簡 renderer 排版。

- 完整：`絕招主彈道改為5道扇形貫穿刀氣，每道造成60%傷害；同一目標最多命中1次`
- 完整：`主彈道命中傷害前：目標防禦降低30%，持續90幀`
- 精簡：`絕招·扇形主彈×5·60%·同目標1次`
- 精簡：`主彈命中·防-30%·90幀`

描述規則：

1. 數字永遠來自 action payload，不接受另外輸入含數值的描述字串。
2. 每個 action variant 必須同時支援執行、驗證及描述；沒有完整描述的 variant 不可合併。
3. 一條規則是顯示分組單位，多個 action 按執行順序組成同一行，避免載入後偷偷展開成使用者看不見的第二效果。
4. 狀態名稱如「寒毒」「枯骨」是穩定語意 ID 的顯示標籤，不包含可調數值。
5. 完整與精簡格式共用同一份語意片段，只改排版，不各寫一個效果 switch。
6. 棋子面板、羈絆面板、裝備、內功 metadata 及觀察文字全部呼叫同一描述入口。

## 統一執行管線

### 事件

沿用目前 `BattleComboTriggerSystem` 已有的機率、次數、固定順序與 runtime 計數，將它重構為唯一的 `BattleEffectSystem`。事件至少包含：

| 事件 | 用途 |
|---|---|
| 常駐／戰鬥初始化 | 羈絆、裝備、內功與永久屬性 |
| 每幀 | 回復、週期行為、限時狀態及區域 |
| 施放規劃 | 內力消耗、遠程化、彈道形狀與目標 |
| 攻擊提交／絕招提交 | 每次出手或絕招只觸發一次的效果 |
| 攻擊生成 | 葵花殘影、區域對新彈道的修正 |
| 命中傷害前 | 穿甲、枯骨、防禦降低、剪盾、攻擊落空 |
| 傷害結算後 | 吸血、受傷記憶、擊殺與命中資源 |
| `HealAttempted／HealApplied` | 寒毒、枯骨、受治療加速；blocked 不作第一版可訂閱事件 |
| 施放延續 | 玉女在第一輪攻擊耗盡後建立一次免費 child cast；每個 cast 只評估一次 |
| 施放結算完成 | 三分不同目標、鐵掌最高傷害 |
| 護盾破裂／單位死亡／友軍死亡 | 既有羈絆及蛤蟆、乾坤 |

不為「羈絆命中」和「絕招命中」建立不同 hook；它們是同一事件，差別只在來源綁定與條件。

### 施放識別

完整契約見[施放來源與結算生命週期設計](施放來源與結算生命週期設計.md)。新增單調遞增的 `BattleCastId`，並以單一 `BattleAttackProvenance` 取代散落來源欄位。同一根施放產生的側翼、延遲、追蹤及追加攻擊都保存：

- `castId` 與根施放 ID。
- 武功 ID、是否絕招、主彈道資格及攻擊序號。
- 效果傳播政策。

延遲佇列、live attack、反彈後代、child cast 與跨幀命令都持有中央 work token；queue → live 只移交 token。所有 work 命中耗盡、失效或取消，且本幀 damage／death transaction 完成後，才發出一次「施放結算完成」，供三分與鐵掌使用。這是共用事件能力，不是 skill-effect 第二管線。

傳播政策：

- 根攻擊：可觸發該來源 store 中符合條件的全部規則。
- 追加攻擊：保留指定傷害／狀態，但不重複觸發根絕招規則。
- 小無相：複製武功攻擊，不載入被選武功的規則。
- 斗轉：不複製武功基礎攻擊，把被選規則以暫時來源綁定掛到本次根施放；複製類 action 被條件排除。

### 命令而非直接改欄位

`BattleEffectSystem` 匹配規則並產生現有戰鬥系統能套用的具型別命令：

- 傷害命令交給 `BattleDamageSystem`。
- 治療命令交給唯一的治療交易。
- 狀態命令交給 `BattleStatusSystem` 的統一套用入口。
- 攻擊命令交給 `BattleCastSystem／BattleAttackSystem`。
- 位移命令交給 `BattleMovement`。

效果 dispatcher 不直接修改其他單位的 HP、MP、位置或狀態，避免規則來源不同時出現不同結算順序。

## 必要的共用結算補強

### 治療

依[治療交易設計](治療交易設計.md)新增唯一的純治療 resolver 與 runtime commit 入口，讓隊伍治療、命中回血、吸血、擊殺回血、死亡醫療及救援治療全部經過同一算法。保留各路徑目前的取整、最少值、事件順序及來源 ID；傷害交易可在自己的 snapshot 內呼叫同一 resolver，不把擊殺回復延後一幀。寒毒與枯骨只是交易中的 typed modifier。

### 狀態

保留現有中毒、流血、冰凍及封內的專用結算，先加一個共用套用／清除入口。新絕招狀態使用具型別 payload；不為了「通用」先重寫所有舊狀態。狀態護盾也在此入口統一攔截負面狀態。

### 傷害

保留現有傷害交易，補上明確的傷害來源分類及規則事件。所有來源合計的減傷在單一最終位置封頂 80%。純粹傷害只忽略防禦，仍經護盾、格擋層、減傷及承傷上限。

### 選擇、區域與移動

- 擴充現有 `BattleProjectileTargetingSystem`，供所有來源共用最低生命／內力、最近／最遠、半徑及不同目標選擇。
- 依[持續區域效果設計](持續區域效果設計.md)新增只負責持有區域狀態及純查詢的 `BattleAreaEffectState／System`；黃沙使用新彈道生成時快照，伏魔使用傷害／位移時 live query。
- 強制拉近擴充現有 `BattleMovement`，不另建平行位移系統。
- 非隨機平手以單位 ID 決定；隨機一律使用 `BattleRuntimeRandom`。

## 遷移順序

### 第一階段：鎖定現有行為

在改資料模型前建立：

- 固定種子的 battle digest、最終 runtime、GUI／headless 一致性基線。
- 每個現有 `EffectType` 的解析、完整／精簡描述及核心結算特徵測試。
- 治療取整、傷害順序、死亡順序、目標平手、彈道取消與隨機消耗順序測試。
- 將舊 parser 固定為只供遷移測試使用的 oracle；把遷移前 top-level 設定凍結為暫時 v1 fixture，先生成 212 個羈絆、130 個裝備及 25 個內功效果的 canonical semantics；包含隱含預設、暗中 expansion、亂數／計數耦合及 runtime ordering。

### 第二階段：共用 schema 與描述器

入口：本計畫開頭六份契約均已評審通過，舊 parser oracle 與行為基線已存在。

1. 在現有 `ChessBattleEffects.*` 中以 `EffectRule` 取代 `ComboEffect`；不新增絕招專用設定模型。
2. 依 typed schema 建立 action／event／selector／condition parser、validator 及唯一 semantic description pipeline；第一個 executable checkpoint 是讓入口門檻的四份 YAML 草稿通過 validator 與自動描述測試，仍不接戰鬥 runtime。
3. 分機制族建立繁體中文 v2 fixture，不先替換遊戲讀取的 `chess_combos.yaml`、`chess_equipment.yaml`、`chess_neigong.yaml`；尚無 executor 的新 schema 不得讓中間 commit 無法執行。
4. 在 v2 fixture 把金幣、刷新、戰場選擇及計作羈絆移出 battle action，並以對應領域的 canonical rule 參與差分。
5. 原方案要求每批執行「v1 YAML → 舊 parser → canonical」與「v2 YAML → 新 parser → canonical」逐條等價比較；實際遷移未保留 oracle 與結果，依[差異與決議](大招效果實作差異與決議.md)不再重建或列為待辦。

這個 schema 遷移會明確更新內容指紋及 replay golden，因為啟用中的規則序列化格式改變；但固定種子 battle digest 與最終 runtime 必須保持一致。這是已知的重播格式相容性中斷，不假裝成零影響重構。

### 第三階段：單一 runtime

1. 沿用並演進已來源無關的 `BattleEffectState`；移除空的 `RoleComboState` subclass 或只做一次性命名清理，不新增另一個 store 實作。
2. 按已驗證的機制族，於同一批變更把 v2 節點提升到 top-level config、替換 runtime consumer，並執行 old-vs-new execution trace；不留下「新 parser 配舊 executor」的中間正式路徑。
3. 把羈絆、裝備、內功及 normal／ultimate 武功規則接入單一 event index／runtime state，刪除平行武功 store。
4. 將 `sumAlways(EffectType)` 等查詢改為屬性／動作鍵查詢，逐類移除舊 `EffectType`。
5. 將 `BattleComboTriggerSystem` 的現有來源無關 reader／commands 演進並整理為唯一的 `BattleEffectSystem`；不平行重寫一套 dispatcher 再切換。
6. 刪除 v1／v2 暫存、test-side exception map、測試 oracle、舊 parser、舊 enum、舊描述 switch 及 runtime registry 中已被統一事件取代的規則，不保留相容 adapter。367 條 canonical／execution trace 證明未在刪除前留存，永久列入差異決議，不以新系統重建假證明。

階段結束時不能同時存在 `ComboEffect` 與 `EffectRule` 兩條正式執行路徑。

### 第四階段：絕招所需共用邊界

這不是一個模糊的「共用補強」批次，而是四個各有獨立 exit gate 的 deliverable：

1. **施放來源**：建立 provenance、中央 outstanding-work tracker、施放完成事件及傳播 truth table；所有現有 attack 建立／複製點通過 lineage 與取消測試。
2. **治療交易**：集中純 resolver 與 commit 入口；八條現有路徑的取整、最少值、來源死亡及事件順序差分完全相同後，才加入寒毒、枯骨與血刀。
3. **持續區域**：建立最小 area owner、geometry 與 query API；黃沙 spawn-time 與伏魔 live-query 的邊界、到期、死亡及重疊測試通過。
4. **其他既有邊界**：補齊統一狀態入口、傷害來源分類、狀態護盾及 80%減傷上限；擴充既有目標選擇、攻擊形狀與強制位移。

四項可以分支實作及獨立評審，但整合時仍只接到同一 `BattleEffectState／BattleEffectSystem`。

### 第五階段：同一系統接入 59 招

先做四條垂直切片：

- 青囊奇術：選擇器＋治療＋自動描述。
- 神照功：施放規劃＋護盾＋自動描述。
- 九陰白骨爪：命中前狀態＋傷害／治療修正＋自動描述。
- 五虎斷門刀：攻擊形狀＋命中狀態＋多 action 描述。

四條都只能使用單一 `BattleEffectStore／BattleEffectSystem`。通過後再按前述四組完成其餘 55 招。

### 第六階段：整體驗證與啟用

1. 真實設定測試確認完整棋池 59 招、簡單棋池 30 招均有規則。
2. 以共用機制族覆蓋正向／負向行為，並對施放生命週期、治療、狀態、傷害、分身、壓制、強制移動與狀態機保留高風險垂直場景；不建立 59 招各一正一負及所有星級排列的窮舉矩陣。
3. 固定種子 GUI／headless digest、最終 runtime 及重播驗證一致。
4. 使用 `.github/build-command.ps1` 進行 Debug 建置並執行完整測試。
5. 59 招實作完成後直接將 `啟用` 改為 `true`，讓絕招規則納入有效內容指紋。
6. 以啟用狀態執行最後一批整體驗證；不另設等待人工評審的停用階段。

## 防膨脹與行為簡化稽核

### 防止另一堆效果

- 正式 runtime 只能有一個效果定義型別、一個 store、一個事件索引及一個描述入口。
- 不允許 `ComboEffectAdapter`、`UltimateEffectAdapter` 等長期轉接層；遷移階段結束即刪除。
- 新 action family 必須服務至少兩個現有效果，或擁有無法拆分的狀態機／全域結算不變量。
- 不預先加入 59 招及現有啟用設定都沒有使用的 action、selector 或 condition。
- 優先刪除舊型別及 switch；每階段檢查正式程式碼增刪行數、新檔案、新型別及引用數。新架構若只增加而沒有移除，該階段不得通過。
- 預期新增的獨立正式系統只有治療交易與區域 owner；效果模型／執行器由現有檔案重構而來，不另建平行目錄。

### 防止偷偷簡化行為

- 純重構前後逐幀 digest 及最終 runtime 必須相同；描述格式及內容指紋的有意變更另列。
- 觸發機率的亂數呼叫次數與順序也屬於行為，不只比較最終勝負。
- 目標、取整、持續時間、最大次數、疊加方法、來源 ID、事件順序及日誌語意逐項比對。
- 不因使用同一 action 就合併不同語意：刺目、玄虛、化勁各自保留消耗條件與後果；五郎承傷上限不等於完整抵擋。
- 不以近似效果代替規格：5×5 不改成圓形、拉近不改成瞬移、延遲攻擊不改成立即多段、逐施放狀態不改成逐施法者狀態。
- 描述測試要證明修改 action 的任一可見數值會同步改變面板文字；設定中不得出現含同一數值的第二份說明。
- 每門武功的場景同時斷言應發生及不應發生的傷害、資源、狀態、目標、重複觸發與來源歸屬。
- `castId` 不能只在根攻擊存在：每個 queue、反彈、延遲、追蹤與取消路徑都要以 work token 證明 settled 不早發、不漏發。
- 治療與區域的純重構分別通過獨立 trace；不得把滿血光環冷卻、固定／即時區域、spawn-time／live-query 等不同語意合併簡化。

## 完成門檻

實作完成需同時滿足以下條件：

- 舊 `ComboEffect／EffectType` 正式管線已移除，羈絆、裝備、內功與絕招共用同一效果模型及 runtime。
- 所有機制文字由解析後規則自動產生；YAML 沒有手寫數值說明。
- 367／367 old-vs-new 證明不再是完成門檻：舊 parser oracle 與基線已刪除，無法有效重建；此永久差異已記錄且不再重複稽核。現況改以真實設定完整載入、唯一性、schema 驗證、共用機制及高風險 runtime 場景為證據。
- 59／59 絕招已實作；真實棋池覆蓋、共用機制場景及代表性負向斷言通過。
- 治療、狀態、傷害、攻擊、位移與死亡沒有繞過共用結算邊界。
- GUI／headless、固定種子 digest 及重播測試通過。
- 程式量稽核沒有發現平行 store、平行 dispatcher、只用一次的通用框架或舊／新雙管線。
- `啟用` 為 `true`，且啟用狀態下的完整 Debug 建置與測試通過。
