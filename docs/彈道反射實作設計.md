## 摘要

「彈道反射」不應吸收或抵消命中反射者的原始彈道。一次成功反射應產生兩次分離的命中：

1. 來襲彈道正常命中反射者，完整執行傷害、防禦、減傷、護盾與命中效果。
2. 原彈道在命中點結束向前生命週期，由反射者從同一位置向原始攻擊者射出一枚回射彈道。
3. 回射彈道命中原始攻擊者時，再作為一次正常命中結算。

「同一枚彈道」是視覺與玩法語意，不是重用同一個 runtime attack ID。回射彈道必須獲得新 ID，並以 `parentAttackId` 指向來襲彈道，避免破壞攻擊生命週期、重複完成 work token 或讓 replay 無法區分來回兩段軌跡。

## 名詞邊界

| 機制 | 現有名稱／型別 | 本設計的意義 |
|---|---|---|
| 彈道反射 | `ProjectileReflectChance`／彈道反射率（`內勁高手`、`大燕傳國玉璽`） | 反射者先承受來襲彈道，再將彈道射回原攻擊者 |
| 彈道彈射 | `ProjectileBounce`／彈道彈射 | 攻擊者的彈道命中後跳往另一名敵人，擁有者不變 |
| 技能反彈 | `SkillReflectPercent`／技能反彈百分比 | 依承受技能傷害百分比立即產生 direct damage 反傷，沒有回程彈道 |
| 彈道互消 | projectile cancellation | 兩枚正在飛行的彈道互相削減或取消 |

以上機制不可共用「反彈」布林值來表示不同語意。新實作應以 attack origin 表示回射來源，不再以傷害種類同時代表「這是一枚回程彈道」。

## 歷史結論

這不是後續 refactor 將原本正確的「先受擊、再回射」行為改壞的 regression：

- `b2f1ef5`（2026-02-19）加入的「技能反彈」是防守者承傷後，另對攻擊者造成一定百分比傷害；它不會重新發射彈道。
- `3322a75`（2026-03-09）首次加入「彈反」／`ProjectileReflect`時，便直接把本應對防守者結算的傷害改到攻擊者，從未建立回程彈道。
- `bb6033b` 與 `54a9f3c` 等後續重構保留該語意，並有測試固定傷害 source／target 對調的結果。

因此，本改動是修正最初對「反射彈道」的實作解讀，不是回復一份曾經存在的 runtime 行為。

## 現況與問題

### 反射目前是傷害轉向

`BattleHitResolver` 目前以下列條件決定是否可反射：

```cpp
operationType == BattleOperationType::RangedProjectile
    || operationType == BattleOperationType::TrackingProjectile
```

成功後，resolver 不對防守者產生正常傷害，而是交換 `sourceUnitId` 與 `targetUnitId`，直接產生 `BattleDamageKind::Reflected` 傷害。這會造成：

- 防守者沒有承受這次彈道命中。
- 沒有回程飛行時間與視覺。
- 原攻擊者沒有第二次命中機會，無法正常格擋、閃避、減傷或以護盾吸收回程彈道。
- 反射者沒有一次真正的 attack-origin hit，因此其命中效果無法正常觸發。

### 攻擊延續早於命中結算

`BattleAttackState::tick` 在產生 `Hit` event 後，立即：

- 標記非貫穿彈道為已消耗；
- 選擇下一個彈射目標；
- 建立 bounce descendant；
- 安排原攻擊的 finish reason。

`BattleCore` 稍後才把同一個 `Hit` 交給 `BattleHitResolver`。因此，當 resolver 知道彈道反射成功時，原彈道可能已經建立不應存在的向前彈射後代。

### 「會移動」不等於目前可反射

現有判斷只讀 `BattleOperationType`，不讀視覺、速度、`track` 或攻擊是否以彈道方式發射。例如，每個 attack-area-type-0 絕招都會自動得到一枚 `MeleeSplash`；它有速度、追蹤與彈道視覺，但 operation type 仍是 `Melee`，因此目前不可反射。

### scripted impact 提前返回

任一攻擊若帶有 `scriptedDamage`、`scriptedStunFrames` 或 `scriptedBleedStacks`，resolver 會在彈道反射判斷之前提前返回。所以 scripted 彈道目前一律不可反射，即使 operation type 是 `RangedProjectile`。

## 目標

1. 將彈道反射改為「正常承受原命中，再發射回程彈道」。
2. 將攻擊形狀、運送方式、payload 種類與反射資格分開。
3. 讓所有可能參與的彈道類別以一份中央 typed policy 決定，不在 spawn site 分散寫布林特判。
4. 保證成功反射會停止原彈道的貫穿與彈射延續。
5. 回射彈道可追蹤到原彈道與原 cast，但不重用 runtime attack ID。
6. 回射彈道的命中擁有者是反射者，並可觸發該單位的合法命中規則。
7. 反射者仍是正常承傷者；彈道反射不提供隱性無敵、免傷或護盾穿透。

## 非目標

- 本文不擴張或縮減現有可反射彈道範圍；後續平衡審查只修改中央 policy function 與對應資料驅動測試。
- 本文不調整 `內勁高手` 或 `大燕傳國玉璽` 的反射率數值。
- 本文不將「技能反彈」改成彈道。
- 本文不讓範圍傷害、DOT tick 或沒有飛行攻擊實體的 effect damage 憑空變成回程彈道。
- 本文不為慕容博或特定羈絆寫專用 hard-coded proc；慕容的 debuff 必須透過現有通用效果事件觸發。

## 反射資格模型

### 運送方式不再借用 operation type

`BattleOperationType` 同時承擔了攻擊形狀、傷害 shaping 與部分呈現語意，不應繼續當作「這是否為可反射的飛行實體」之唯一資訊。

delivery 與 payload 的 value type 放在新的 `src/battle/BattleAttackDelivery.h`。它們是 attack 建立契約的一部分，不是反射系統私有的附加布林。中央資格政策則放在 `src/battle/BattleProjectileReflectionPolicy.h/.cpp`。

建議新增：

```cpp
enum class BattleAttackDeliveryKind
{
    Contact,
    Projectile,
    Effect,
};

enum class BattleProjectilePayloadKind
{
    Combat,
    ScriptedDamage,
    ScriptedControl,
};

enum class BattleAttackReflectionLineageKind
{
    Ordinary,
    ReflectedReturn,
};

class BattleAttackDelivery
{
public:
    BattleAttackDelivery() = delete;

    static BattleAttackDelivery contact();
    static BattleAttackDelivery projectile();
    static BattleAttackDelivery effect();

    BattleAttackDeliveryKind kind() const;

private:
    explicit BattleAttackDelivery(BattleAttackDeliveryKind kind);
    BattleAttackDeliveryKind kind_;
};

class BattleProjectilePayloadClass
{
public:
    BattleProjectilePayloadClass() = delete;

    static BattleProjectilePayloadClass combat();
    static BattleProjectilePayloadClass scriptedDamage();
    static BattleProjectilePayloadClass scriptedControl();

    BattleProjectilePayloadKind kind() const;

private:
    explicit BattleProjectilePayloadClass(BattleProjectilePayloadKind kind);
    BattleProjectilePayloadKind kind_;
};

struct BattleProjectileReflectionDescriptor
{
    BattleAttackDelivery delivery;
    BattleProjectilePayloadClass payloadClass;
    BattleOperationType operationType;
    BattleAttackCastSubrequestKind subrequestKind;
    BattleAttackOriginKind origin;
    BattleAttackReflectionLineageKind reflectionLineage;

    BattleProjectileReflectionDescriptor(
        BattleAttackDelivery delivery,
        BattleProjectilePayloadClass payloadClass,
        BattleOperationType operationType,
        BattleAttackCastSubrequestKind subrequestKind,
        BattleAttackOriginKind origin,
        BattleAttackReflectionLineageKind reflectionLineage);
};
```

`BattleProjectilePayloadClass` 是新的「payload 分類」value type；既有 `src/battle/BattleAttackSystem.h` 中承載 attack data 的 `struct BattleAttackPayload` 保留原名，不搬移、不重新定義。新的 classification 以明確命名避免與該既有 struct、`BattleAttackSpawnRequest::initial`、`BattleAttackInstance::state` 及 `HeadlessBattleRunner` digest 路徑衝突。

既有 struct 只新增必填分類欄位，其餘 attack data members 與 consumer type name 維持原位：

```cpp
struct BattleAttackPayload
{
    BattleAttackDelivery delivery;
    BattleProjectilePayloadClass payloadClass;
    BattleAttackReflectionLineageKind reflectionLineage;

    // 既有 attackSourceUnitId、skill metadata、projectile state……
};
```

`BattleAttackDelivery`、`BattleProjectilePayloadClass`、`BattleProjectileReflectionDescriptor` 與包含分類的 `BattleAttackSpawnRequest` 均不可 default-construct。每個 spawn site 必須以 constructor／factory 明確提供 delivery、payload class 與 reflection lineage；同一 projectile state 的 clone／bounce／continuation 必須複製這份 typed lineage。既有 default-construction site 在本改動中一併遷移。未來新增 attack 卻漏填分類時，應直接編譯失敗，不能靜默套用 `Contact`／`Combat`／`Ordinary` 或「不可反射」等假預設。

`delivery` 表示實際運送方式；`operationType` 繼續負責現有傷害 shaping 與戰鬥形狀。兩者可以不同，例如 melee ultimate splash 可以保留 `BattleOperationType::Melee` 傷害形狀，但 delivery 是 `Projectile`。

中央政策使用完整 descriptor 決定資格：

```cpp
bool BattleProjectileReflectionPolicy::allows(
    const BattleProjectileReflectionDescriptor& descriptor) const
{
    if (descriptor.reflectionLineage
            == BattleAttackReflectionLineageKind::ReflectedReturn
        || descriptor.delivery.kind() != BattleAttackDeliveryKind::Projectile
        || descriptor.payloadClass.kind() != BattleProjectilePayloadKind::Combat)
    {
        return false;
    }

    return descriptor.operationType == BattleOperationType::RangedProjectile
        || descriptor.operationType == BattleOperationType::TrackingProjectile;
}
```

上述初始實作有意保留今日行為：只有 non-scripted `RangedProjectile` 與 `TrackingProjectile` 可反射。差別在於該規則只存在這個中央 function，resolver 與各 spawn site 不再各自猜測資格。未來若要開放例如 P10，只需在此處依 typed descriptor 新增明確分支，不需改寫 hit resolver 主流程。

未來重新審查時，只需修改 `BattleProjectileReflectionPolicy::allows` 並更新本表與資料驅動測試；實作不應再需要改動 resolver 主流程。

## 攻擊來源與生命週期

### 新的 reflection origin

```cpp
enum class CastOriginKind
{
    // 現有值……
    Reflection,
};

enum class BattleAttackOriginKind
{
    // 現有值……
    Reflection,
};
```

第一枚回射彈道的 immediate attack origin 必須是 `Reflection`，且 `reflectionLineage == ReflectedReturn`。如果它依繼承的 projectile properties 產生 bounce／continuation clone，descendant 可以使用 `Bounce` 等正確 immediate origin，但必須繼續複製 `ReflectedReturn` lineage。

中央反射政策對整條 `ReflectedReturn` lineage 固定返回 false；此條件不屬於 P01–P15 的可調政策。不能只檢查 `origin == Reflection`，否則 immediate origin 已改成 `Bounce` 的回程後代會重新取得反射資格，造成反射—彈射—再反射的 ping-pong。

`ReflectedReturn` 跟隨「同一枚回程彈道的 continuation lineage」，不是污染整個 reflection child cast。若反射者自己的合法 hit rule 另外建立一枚獨立 attack，而且不是由回程彈道的 projectile state clone／continue 出來，該新 attack 必須明確宣告自己的 ordinary lineage，再依 P01–P15 中央政策判定；不能只因它與回程命中同屬一個效果處理流程便自動禁止反射。

### 回射建立 reflector-owned child cast

原彈道的 cast 來源是原攻擊者，但回程命中必須由反射者擁有。直接把回程 attack 塞回原 cast 會讓 cast source、實際攻擊者與傷害 aggregate 互相矛盾。

因此，成功反射應建立 child cast：

```cpp
BattleChildCastRequest{
    .sourceUnitId = reflectorUnitId,
    .magicId = -1,
    .ultimate = false,
    .origin = CastOriginKind::Reflection,
    .propagation = CastPropagationPolicy::SourceHitRulesOnly,
};
```

其生命週期契約為：

- child cast 的 `parentCastId` 是來襲彈道所屬 cast。
- child cast 與原 cast 共用 `rootCastId`，使 replay 與生命週期可追蹤完整來回關係。
- child cast 擁有自己的 aggregate，回程傷害不計入原攻擊者 cast 的傷害與命中目標統計。
- 原 cast 等待 reflection child 完成後才最終 settled，但不合併 child aggregate。
- `SourceHitRulesOnly` 允許 `MainProjectileBeforeDamage`、`HitBeforeDamage`、`DamageResolved` 等命中事件，不重跑 cast commit、ultimate commit、免費重施或原絕招擴張規則。
- `magicId = -1` 表示這個 synthetic child cast 不是「再次施放來襲武功」。來襲彈道的 `skillId`、武功名稱、magic power、hurt type 與視覺仍保留在 attack payload metadata，不能回填成 child cast 的 magic identity。
- 原攻擊者綁定該 `magicId` 的規則，即使具有 non-owner observation scope，也不得因 reflection child 的事件再觸發。`SourceHitRulesOnly` 只開放反射者所擁有的通用 combo／裝備／角色命中規則。
- child attack 的 `parentAttackId` 指向來襲 attack，`mainProjectile` 固定為 false，避免回程彈道假裝成反射者自己 cast 的主彈。

這是一種跨單位的 child cast；`BattleCastLifecycle` 目前不要求 child 與 parent 具有相同 `sourceUnitId`，但必須新增正向與 invariant 測試把這個用法固定下來。

### 原彈道的完成原因

成功反射時，來襲 attack 以新的明確原因終止：

```cpp
enum class AttackFinishReason
{
    // 現有值……
    ReflectedAtHit,
};
```

不可把它記為 `ProjectileCancelled`，因為原命中已被接受並正常結算；也不可只記為 `SpentOnHit`，因為 replay／戰報與生命週期測試需要區分普通消耗與彈道反射。

## payload 與擁有權分離

回射彈道同時需要兩組不同來源的資料：

| 資料 | 來源 |
|---|---|
| 視覺特效、skill ID／名稱、hurt type、magic type 等 presentation／skill metadata | 來襲彈道的既有 `BattleAttackPayload` |
| 基礎 potency seeds：effective attack、magic power | 來襲彈道在原 accepted contact、任何 defender／act-property／flight shaping 前凍結的 `BattleAttackPotencySnapshot` |
| 速度、追蹤、operation、strength、projectile-cancel weaken、`totalFrame`／flight-decay policy、bounce／through 等 projectile shaping／continuation state | 反射點 materialized projectile-properties snapshot；回程 runtime frame 依下述規則重設後重新 shaping |
| `attackSourceUnitId`、傷害擁有者、戰報輸出擁有者 | 反射者 |
| 暴擊率／倍率、攻擊性冷卻延長、斬殺門檻、造傷 modifier 與其他 attacker-side hit-time 數值 | 反射者在回程命中時的數值 |
| attacker act property | 回程命中時反射者對該 magic type 的 live act property |
| defender act property | 回程命中時原始攻擊者對該 magic type 的 live act property |
| `HitBeforeDamage` 提供的 `ignoreDefensePct` | 反射者 |
| 命中與 `DamageResolved` 規則擁有者 | 反射者，即使回程命中時反射者已死亡 |
| 防禦、閃避、格擋、護盾、承傷 modifier 與其他 defender-side 數值 | 原始攻擊者在回程命中時的數值 |
| 回程目標 | 原始攻擊者 |
| provenance | reflection child cast／attack |

### 回程命中數值歸屬決議

回程命中的 live attacker 是反射者（例如慕容博），不是原始攻擊者。所有在命中階段透過 `event.sourceUnitId` 讀取或由 attacker-owned 規則提供的數值，都必須從反射者取得，包括：

- 暴擊率與暴擊倍率；
- 攻擊性冷卻延長的機率與延長量；
- 斬殺門檻；
- attacker-side 造傷加成／減益；
- `HitBeforeDamage` 與其他合法 hit rules 產生的 attacker-side modifier；
- 對 incoming magic type 的 attacker act property；
- `ignoreDefensePct`。

因此，慕容博的暴擊數值可以作用在他回射的彈道上。暴擊、傷害浮動與其他每 hit random value 都重新獨立擲骰，不沿用來襲命中的結果。原始攻擊者在回程階段只作為 defender，其 live 防守數值正常參與結算。

來襲彈道保留的 `BattleAttackPotencySnapshot` 是「同一枚彈道所攜帶的基礎威力」，不是把原始攻擊者繼續當作回程命中的 live attacker。不可只把 `attackSourceUnitId` 改成慕容後，再用慕容當下攻擊力／武功重新建立一枚完全不同的彈道；也不可在回程命中時重新讀取原始攻擊者的 attacker-side stats。這個邊界保留回射原彈道的 payload，同時讓反射者完整決定回程 hit-time stats、act-property matchup 與 rules。

### potency snapshot 與 hit shaping 邊界

`BattleAttackPotencySnapshot` 必須在原 accepted contact 上、任何 defender-specific 或 hit-shaping 計算之前建立，內容只包括：

```cpp
struct BattleAttackPotencySnapshot
{
    int effectiveAttack;
    int magicPower;

    BattleAttackPotencySnapshot(int effectiveAttack, int magicPower);
};
```

- `effectiveAttack`：原始攻擊者在來襲 accepted contact 時，套用當下合法 Attack attribute modifiers 後的 attack stat。
- `magicPower`：來襲 `BattleAttackPayload::skillMagicPower`；它是原彈道既有的 skill potency seed，不改成反射者自己的武功威力。

snapshot 明確不包含：

- defender defense 或 `ignoreDefensePct`；
- attacker／defender act property 或兩者差值；
- `projectileCancelDamage`／累積 `projectileCancelWeaken`；
- `strengthPct`、operation damage shaping、impact facing；
- `frame`／`totalFrame` flight decay；
- base-damage variance、final hit variance、暴擊或任何 outgoing／incoming modifier。

上述排除項都在每次實際命中依該 leg 的 live participants、projectile state、geometry 與獨立 random draws 重新計算。建議將現有「以攻擊者攻擊力、武功威力與目標防禦一次算出 base damage」的邏輯拆成：

```cpp
BattleAttackPotencySnapshot snapshotAttackPotency(...);
int resolveAttackPotencyAgainstDefender(
    const BattleAttackPotencySnapshot& potency,
    const BattleRuntimeUnit& defender,
    int ignoreDefensePct,
    BattleRuntimeRandom& random);
```

原命中與回程命中都使用相同 potency seeds，但各自使用當下目標防禦、穿防與 base-damage variance 解出 defender-specific base damage，再進入 `shapeHitDamage`。回程命中仍是一次新 hit，因此依現有每次命中規則獨立評估暴擊、格擋、閃避、final variance 與其他 hit-time modifier。

act-property shaping 明確使用回程的 live ownership matchup：

```text
attackerActProperty = actPropertyForMagicType(reflector, incoming.magicType)
defenderActProperty = actPropertyForMagicType(originalAttacker, incoming.magicType)
```

回程路徑不得沿用來襲 `event.skillAttackerActProperty`。`makeHitSkillSnapshot` 應由 caller 明確提供上述 resolved pair，或由 reflection-lineage-aware builder 取得；不能再讓 copied incoming field 優先於 reflector 的 live act property。這保證 potency 在 act-property shaping 前凍結，而屬性相剋由慕容博對原始攻擊者的當下 matchup 決定。

projectile shaping 則依回程 instance 處理：

- 反射點累積的 `projectileCancelWeaken`、`strengthPct` 與 operation 等 materialized state 複製到回程 attack；回程中若再次互消，可繼續累積 weaken。
- 回程是新的一段 launch leg：runtime `frame` 從 0 開始，複製原彈道設定的 `totalFrame`，flight-frame decay 依回程實際飛行幀數重新計算；來襲 leg 已消耗的 flight decay 不凍結進 potency，也不疊加到回程起始 frame。
- impact facing／side／back shaping 使用回程接觸位置與原始攻擊者命中時的 live facing。

`ignoreDefensePct` 不進入 potency snapshot。原命中由原始攻擊者的 `HitBeforeDamage` 規則決定穿防；回程命中重新派發反射者的 `HitBeforeDamage`，再把反射者本次產生的 `ignoreDefensePct` 傳給 `resolveAttackPotencyAgainstDefender`。明確結果如下：

- 原始攻擊者有穿防、反射者沒有：回程命中不繼承原始攻擊者的穿防。
- 反射者有穿防、原始攻擊者沒有：回程命中使用反射者的穿防。

## 傷害種類與正常防守

回射彈道不應使用目前的 `BattleDamageKind::Reflected`。該種類現在會讓傷害繞過部分正常防守，例如雙手格擋與護盾吸收；這符合「立即反傷」的舊語意，不符合「一枚實際飛回來的彈道」。

回程 attack 應：

- 保留來襲彈道的正常 `Physical`／`Skill`／其他 payload damage kind；
- 以 `BattleAttackOriginKind::Reflection` 表示它來自彈道反射；
- 可被原攻擊者閃避、格擋、減傷、護盾與承傷上限正常處理；
- 在戰報與分析中依 attack origin／lineage 標示「彈道反射」，讓 immediate origin 已變成 `Bounce` 的回程後代仍可追溯，不要改靠 damage kind 猜測。

### reflected-damage 舊基礎設施刪除決議

實作稽核確認，現有 projectile source／target swap 是 `BattleDamageKind::Reflected` 唯一 producer。`SkillReflectPercent` 的直接技能反傷實際上產生沒有 attack provenance 的普通 `Physical` damage，並不使用該 kind。`BattleDamageRequest::reflected` 雖然被讀取，卻沒有任何 writer；所以 `AcceptedHitCondition::excludeReflected` 與作者語法「排除反彈」目前也無法排除 `SkillReflectPercent`。

依專案不保留舊相容層的規則，本改動直接刪除下列死語意，不將它們重新命名或轉接：

- `BattleDamageKind::Reflected`；
- `BattleDamageRequest::reflected`；
- `BattleDamageDefenseInput::reflected` 及只對 reflected damage 生效的防守 bypass；
- `DamageChannel::Reflected` 及其 parser、display、schema mapping；
- `AcceptedHitCondition::excludeReflected`；
- `config/chess_*.yaml` 中所有 `排除反彈: true` 欄位。

`SkillReflectPercent` 維持現有的 provenance-free direct-damage 機制。它沒有 accepted attack-hit provenance，因此不能滿足 `AcceptedHitCondition`；已刪除的 exclude filter 對它原本就是冗餘的。若未來要替直接技能反傷新增條件，應先建立獨立的 typed damage origin，再以 origin 匹配，不能復活或借用 projectile reflection 的 damage kind。

回程彈道則保留 payload 的正常 damage kind，反射身分由 immediate `BattleAttackOriginKind::Reflection` 與可向後代傳遞的 `ReflectedReturn` lineage 表示。既有 reflected-kind 測試要遷移為「正常 damage kind + reflection attack provenance」的斷言。

### 彈道反射與技能反彈獨立觸發

兩個設定處理不同輸入、產生不同輸出，不設互斥：

| 設定 | 觸發基準 | 輸出 |
|---|---|---|
| `ProjectileReflectChance` | 一枚符合中央政策的 projectile 形成 accepted contact | 正常承受原命中後，另建立有飛行時間的回程 attack |
| `SkillReflectPercent` | 依既有規則取得本次承受技能傷害 | 立即按承傷百分比產生 provenance-free direct damage，沒有 projectile |

同一次來襲技能同時滿足兩者時，兩者各自正常執行：防守者先正常承傷，`SkillReflectPercent` 依自己的承傷規則產生直接反傷，`ProjectileReflectChance` 則建立回程彈道。任何一方都不能因另一方成功而短路、取消或消耗對方。最終承傷為 0 時，直接技能反傷仍遵守它既有的承傷百分比語意；該結果不影響 accepted-contact projectile reflection。

現有 resolver 以 `!result.reflected` gate `SkillReflectPercent`，同時也 gate execute、defender block 與部分正常 hit follow-up；這些都是舊「傷害改道」語意留下的 coupling。新實作必須移除這些 gates：彈道反射成功只改變原 attack 的 continuation，不取消來襲 accepted hit 的任何正常結算。若某個效果自身另有 typed 條件，繼續由該條件決定，不能再把 `result.reflected` 當成通用 suppression flag。

## 慕容 debuff 的觸發契約

`config/chess_combos.yaml` 的四人「姑蘇慕容·以彼之道還施彼身」目前在 `DamageResolved` 之後對命中目標施加造成傷害降低 45%、持續 70 幀的 modifier。規則要求：

- 傷害方位是造成；
- 傷害來自已接受的 attack hit；
- 實際生命傷害大於 0。

`SkillReflectPercent` 沒有 accepted attack-hit provenance，原本就不能滿足此 `AcceptedHitCondition`；刪除 `excludeReflected` 後不需要替這條慕容規則新增替代 filter。

回射彈道命中原攻擊者時，效果 context 必須滿足：

```text
event owner             = 反射者（例如慕容博）
damage attackerBefore  = 反射者
damage origin           = EffectAttackDamageOrigin(reflection attack provenance)
damage kind             = 來襲彈道的正常傷害種類
propagation             = SourceHitRulesOnly
accepted hit            = true
```

如此一來，慕容的 debuff 會透過現有 `DamageResolved` 規則正常觸發，不需要 `if (unitId == 113)` 或根據裝備 ID 特判。

這也意味著：反射者其他同樣合法的 `HitBeforeDamage`／`DamageResolved` 規則會依自身條件正常評估。這是 reflector-owned hit 的一致語意，不只是為慕容 debuff 打開單一例外。另一方面，cast commit、ultimate commit 與大招攻擊擴張不屬於 hit rules，不會因回射而重複觸發。

## 命中偵測與延續結算分離

### 新結算邊界

`BattleAttackState::tick` 只負責：

1. 移動 attack。
2. 偵測接觸目標。
3. 標記本幀的 pending contact。
4. 產生 `Hit` event。

它不再於產生 `Hit` 的同一段邏輯中建立 bounce descendant 或決定非貫穿彈道的最終 finish reason。

Core 完成 suppression、dodge 與 hit resolution 後，必須對每個 pending contact 回傳一份 typed settlement：

```cpp
enum class BattleHitContinuation
{
    Normal,
    Reflected,
};

struct BattleHitSettlement
{
    int attackId{};
    int targetUnitId{};
    bool accepted{};
    BattleHitContinuation continuation{};
};
```

`BattleAttackState::settleHit` 再依 settlement：

- `Normal`：執行現有 through／bounce／spend-on-hit 邏輯。
- `Reflected`：停止原 attack，清除向前 bounce／through 延續，回傳一份 reflection spawn descriptor。

這份 API 也必須覆蓋被 suppression 或 dodge 消耗的命中，保證每個 pending contact 都恰好結算一次，不留下永久 pending 的 attack。

現況是 attack state 先決定 bounce，Core 才得知該接觸是否閃避；所以一次後來被判定為 dodge 的接觸仍可建立 bounce descendant。拆分 settlement 後必須保留這項 normal-path 玩法：dodged contact 的 `accepted = false`，不能擲反射率，但 continuation 仍回傳 `Normal`，照常執行既有 bounce 選擇、次數消耗與 spend 行為。不得因「未 accepted」而提前結束，或順手取消原本會建立的 bounce descendant。

### accepted contact 是唯一反射承諾邊界

`ProjectileReflectChance` 在命中已通過 suppression／dodge、成為 accepted contact 時判定，不等待 `BattleDamageSystem` 算出最終 HP delta。這是最直接的實作邊界：resolver 可以一次回傳 normal damage commands 與 reflection request，不需要在 damage reducer 之後再反向查找 pending attack、補建 child cast 或重排 continuation。

因此，格擋、護盾、承傷上限或其他 defense reducer 即使把原命中的最終 HP 傷害降為 0，已成功的彈道反射仍會發射。只有 suppression／dodge 等令 contact 不被接受的結果不會擲反射率。`SkillReflectPercent` 是否產生非零直接反傷仍由它自己的實際承傷語意決定，不能反過來成為彈道反射的 gate。

### 成功反射的延續規則

- 來襲 runtime attack 在反射者處結束；它不再以原攻擊者擁有的 attack 身分繼續向前貫穿，也不建立原方向的 bounce descendant。
- 在 `Reflected` settlement 消耗原 attack 前，先擷取一份 typed projectile-properties snapshot。回程 attack 複製反射點當下已實體化在彈道上的速度、追蹤、碰撞、射程／lifetime、互消策略、`through`、剩餘 `bounceRemaining`、retarget／preferred-target policy，以及既有彈道削弱／延續資料。
- 這裡只繼承 attack instance 已具備的 projectile properties，不重新讀取原始攻擊者的角色規則，也不把原始攻擊者的 character stats 複製給反射者。
- 回程 attack 的初始目標與初始方向指向原始攻擊者；之後是否貫穿、彈射或在目標消失時重選，完全依繼承的 projectile properties 執行，不強制覆寫成 `through = false`、`bounceRemaining = 0` 或 `requirePreferredTarget = true`。
- 回程 attack 使用新 runtime ID，因此不複製來襲 attack 已命中的 unit history；但 bounce／through 等剩餘 budget 取反射 contact 當下、尚未執行原方向 `Normal` settlement 前的值。
- 回程彈道及其 bounce／continuation clones 都由反射者擁有，後續正常目標選擇以反射者的敵方（即原始攻擊者一方）為候選。因此，原彈道若具有 bounce／pierce 性質，回程也可能命中原始攻擊者一方的多個單位。
- 回程 attack 設為 `reflectionLineage == ReflectedReturn`；它建立的每一層 bounce／continuation clone 必須複製此 lineage。它們可以正常彈射，但中央政策永遠不允許這條 lineage 再次觸發 `ProjectileReflectChance`。
- 反射在 accepted contact 時已承諾；即使原命中於同一個 reducer pass 殺死反射者，Core 仍必須建立已 reserve 的 reflection child／attack。
- 反射者在回程發射前或飛行期間死亡時，回射彈道依既有「已發射 attack 不因 source 死亡而取消」的規則繼續飛行。

這項契約允許回程彈道保留原有彈道個性，但禁止「反射後 bounce，bounce 後又被反射」的多重反射 ping-pong。禁止的是第二次反射，不是原彈道本來就具有的 bounce／pierce。

### 死亡反射者的命中規則

回程 attack 在 accepted contact 時取得 reflector-owned provenance；反射者之後死亡不改寫或清空這份擁有權。回程命中時，即使 `sourceUnitId` 對應單位已死亡，仍要：

- 讀取該反射者的 attacker-side hit stats；
- 派發該反射者的 `HitBeforeDamage`／`DamageResolved` 等合法 hit rules；
- 以該反射者作為 damage／debuff source owner。

因此，若原命中殺死慕容博，他在該 accepted contact 承諾的回程彈道仍可造成傷害，並在符合正生命傷害等既有條件時施加「姑蘇慕容」debuff。這不是死者發起新 cast，而是已承諾、已建立 lineage 的 attack 完成命中；其他 modifier 是否仍有效，繼續遵守各 modifier 本身的 lifetime，不在此處額外延長。

## 建議的每幀順序

1. `BattleAttackState::tick` 移動彈道並產生 pending `Hit`，但不建立 bounce。
2. Core 處理 typed suppression 與 dodge。未被接受的 hit 不反射。
3. Core 派發原攻擊者的 `MainProjectileBeforeDamage`／`HitBeforeDamage` 規則。
4. `BattleHitResolver` 正常建立對反射者的傷害與副作用命令；若同時符合 `SkillReflectPercent`，也依其既有契約建立獨立 direct-damage command。
5. resolver 依中央政策與反射率擲骰，另外填入 `BattleHitResolutionResult::reflection`；此判定不等待最終 HP delta，也不修改或短路第 4 步的任何輸出。
6. Core 將 `Normal`／`Reflected` settlement 回傳 attack state；`Reflected` 回傳原方向消耗前的 projectile-properties snapshot。
7. 若反射成功，Core 先建立 reflection child cast、reserve child attack work，再以繼承的 properties 與 `ReflectedReturn` lineage 將回射 request 公開到 attack queue。
8. 本幀 damage reducer 正常完成反射者承受的原始傷害。
9. 回射彈道從命中點開始於後續 tick 飛行，命中原攻擊者後建立第二份獨立 damage transaction。
10. 第二次命中以反射者（包括已死亡的反射者）作為 `event.sourceUnitId`，重新評估其 attacker-side hit stats／rules；原始攻擊者的 magic-bound rules 不參與。

第 4 與第 8 步保證「反射」不會再把原傷害從防守者身上移除；第 9 步才是由慕容擁有且能帶出 debuff 的回程命中。

## 互動契約

| 情況 | 行為 |
|---|---|
| 來襲命中被閃避 | 沒有 accepted hit，不觸發彈道反射；仍以 `Normal` settlement 保留現有 bounce／spend 延續 |
| 來襲命中被格擋、護盾或承傷上限化解 | 已接受彈道命中；反射率依 contact 擲骰，不要求最終 HP 傷害大於 0 |
| 來襲命中導致反射者死亡 | 反射在 accepted contact 時已承諾，回程彈道仍發射；與同幀互相擊倒語意一致 |
| 來襲彈道可貫穿 | 原 runtime attack 在反射者處停止向前；回程 attack 繼承 `through` 並可沿回程方向正常貫穿 |
| 來襲彈道有 bounce remaining | 不建立原方向 bounce；回程 attack 繼承反射點當下的剩餘 budget，之後可向反射者的敵方正常彈射 |
| 原始攻擊者在回程命中前消失 | 依原彈道已具備的 preferred-target／retarget property 決定 `TargetLost` 或重選，不強制覆寫 |
| 回程彈道或其 bounce descendant 命中另一名反射者 | `reflectionLineage == ReflectedReturn` 固定不可再次反射 |
| 回程彈道遭 projectile cancellation | 依它保留的彈道 payload 正常互消；若原彈道明確忽略互消，回程也保留該特性 |
| 回程彈道命中 | 原攻擊者可正常閃避、格擋、減傷與以護盾吸收 |
| 同一次來襲技能同時滿足 `SkillReflectPercent` | 不互斥；直接技能反傷與回程彈道依各自契約同時觸發 |

上表均為已固定的實作契約。回程彈道可以繼承 bounce／pierce／retarget 等 projectile properties；固定禁止的是整條 reflection lineage 再次反射。

### 隨機序列與 replay 相容決議

將 bounce／continuation 擲骰從 `tick` 移到 settlement，可能改變同幀其他隨機抽取的先後順序。依專案的無向後相容政策，本改動不模擬舊 draw order，也不保證舊 replay 產生相同結果。實作時應更新 replay version／deterministic digest 與所有固定 seed 期望；新契約只保證相同新版本、相同 seed 與相同輸入得到一致結果。

## resolver 輸出

`BattleHitResolutionResult::reflected` 目前同時表示「擲骰成功」與「傷害已改道」。新實作不再有後一種語意，應改成明確的延續請求：

```cpp
struct BattleProjectileReflectionRequest
{
    int incomingAttackId;
    int reflectorUnitId;
    int originalAttackerUnitId;
    Pointf contactPosition;
    BattleAttackPotencySnapshot potency;
};

struct BattleHitResolutionResult
{
    // 原有輸出……
    std::optional<BattleProjectileReflectionRequest> reflection;
};
```

resolver request 是「反射判定與 combat payload」半邊；`BattleAttackState::settleHit(Reflected)` 則按 `incomingAttackId` 回傳包含 `BattleProjectilePropertiesSnapshot` 的 spawn descriptor。該 snapshot 必須在原方向 continuation 前擷取，保存 materialized projectile properties 與剩餘 budget。Core 合併兩份 typed output 建立 reflector-owned return attack，並明確設置 `reflectionLineage = ReflectedReturn`。

resolver 仍可產生「彈反」浮動字與 log event，但不再從 `reflection` 推導原傷害應改成對原攻擊者。

## 不同 payload 路徑

中央反射判斷必須移到 scripted／non-scripted 共用的命中前導路徑，否則 P14／P15 即使未來被決定為可反射，也永遠沒有進入政策的機會。

但是，政策「允許某類 scripted 彈道」不等於將它轉成普通技能傷害：

- combat projectile 保留 combat potency／skill shaping。
- scripted-damage projectile 保留 scripted damage payload 與 modifier policy。
- scripted-control projectile 保留 stun／bleed payload。
- 三者的回程擁有者都是反射者，並使用 reflection provenance。

若政策最後排除 P14／P15，這份結構仍可保證「排除」來自中央政策，不是 resolver 提前返回的偶然副作用。

## 測試計畫

### resolver 單元測試

- 100% 彈道反射時，原傷害 command 的 source 仍是原攻擊者，target 仍是反射者。
- 成功反射另外回傳 reflection request，不直接對原攻擊者產生 HP damage command。
- 0% 與失敗擲骰不產生 reflection request。
- `reflectionLineage == ReflectedReturn` 時，即使 immediate origin 已變成 `Bounce` 且對方反射率為 100%，也不產生第二次 reflection。
- scripted／non-scripted 都會進入中央政策，最終結果完全取決於政策表。
- 回程傷害保留來襲 payload 的正常 damage kind，不再存在 `BattleDamageKind::Reflected` producer 或 assertion。
- 同一 accepted hit 同時具有 100% `ProjectileReflectChance` 與非零 `SkillReflectPercent` 時，結果同時包含 reflection request 與既有 direct skill-reflect damage；任一效果都不短路另一效果。
- 對相同 accepted hit 比較 0%／100% projectile reflection：除了新增 reflection request 與 continuation settlement 外，原命中的 execute、defender block 與合法 normal hit follow-up 輸出一致，證明舊 `!result.reflected` suppression 已移除。
- accepted contact 的 normal damage 最終被 defense reducer 化為 0 時，reflection request 仍然存在；suppressed／dodged contact 才不產生 request。

### attack state 單元測試

- `tick` 產生 hit 後不會在 settlement 前建立 bounce。
- `Normal` settlement 保留現有貫穿、非貫穿消耗與 bounce 行為。
- 會 bounce 的 contact 即使被 dodge，仍以 `accepted = false`、`continuation = Normal` 建立與現況相同的 bounce descendant 並消耗相同 bounce 次數；同時不產生 reflection request。
- `Reflected` settlement 將原 attack 以 `ReflectedAtHit` 完成，不建立原方向 bounce，並回傳消耗前的 projectile-properties／remaining-budget snapshot。
- 回程 request 從 contact position 出發，速度大小保留，方向對準原攻擊者。
- 以 table-driven case 驗證回程 attack 使用新 ID、reflection origin、正確 `parentAttackId`，並逐項繼承 `through`、`bounceRemaining`、tracking、retarget／preferred-target、互消、射程／lifetime 與彈道削弱資料。
- 回程 attack 複製 `totalFrame` 與反射點累積的 `projectileCancelWeaken`／`strengthPct`，但新 runtime `frame == 0`；後續 hit 使用回程 leg 自己的 elapsed frame 計算 decay。
- 回程 attack 的 contact history 為空，但 remaining bounce／through budget 等於來襲 attack 在 reflected settlement 前的值。
- 原彈道允許 bounce／pierce 時，回程可以對反射者的敵方正常建立 continuation；該 continuation 的 immediate origin 可為 `Bounce`，但 `reflectionLineage` 仍為 `ReflectedReturn`。
- 原始攻擊者消失時，分別驗證繼承 `requirePreferredTarget` 的 `TargetLost` path，以及允許 retarget 的正常重選 path。
- pending contact 無論 normal、reflected、dodge 或 suppression 都恰好 settlement 一次。

### lifecycle 單元測試

- reflection child cast 保留原 root cast，但 source unit 是反射者。
- reflection child cast 的 `magicId == -1`，incoming `skillId` 只存在 return attack payload metadata。
- parent cast 在 reflection child attack 完成前不 settled。
- child aggregate 不合併到 parent aggregate。
- return target lost、projectile cancellation、battle end 各自正確完成 child work，沒有 token leak 或重複完成。

### 效果整合測試

- 慕容博成功反射後，自身正常承受來襲彈道的實際傷害。
- 來襲命中被護盾／格擋完全化解為 0 HP 傷害時，只要 contact accepted 且反射擲骰成功，慕容博仍建立回程彈道。
- 回程彈道命中原攻擊者並造成正生命傷害後，觸發「姑蘇慕容」四人 45% 造傷降低、持續 70 幀的 debuff。
- 回程彈道被閃避、格擋或完全吸收而沒有正生命傷害時，不觸發該 debuff。
- debuff 的 source owner 是慕容博，target 是原攻擊者，不是來襲彈道的原始目標。
- 回程命中不觸發 cast commit／ultimate commit，不生成原彈道絕招的側翼或額外彈道。
- 在原始攻擊者掛上一條綁定 incoming `magicId`、具有 non-owner observation scope 的規則；回程 cast／hit 後其 activation count 不變，證明原始攻擊者的 magic-bound rules 不會觀察到 synthetic reflection cast。
- 將來襲傷害設為致死：慕容博死亡後，已承諾的回程彈道仍命中、造成傷害，並以死亡的慕容博為 owner 施加「姑蘇慕容」debuff。
- 使用具有剩餘 bounce 的來襲彈道：回程命中原始攻擊者後可依繼承 budget 彈向其隊友；每一個造成正生命傷害的 reflector-owned continuation hit 都可觸發慕容博的合法 debuff，但任何目標的 100% 彈道反射率都不能把這條 `ReflectedReturn` lineage 再射回去。
- 不以慕容、角色 113 或裝備 196 的 ID 特判測試通過路徑；替代反射者擁有同類通用 hit rule 時也能觸發。

### 回程數值歸屬測試

- `BattleAttackPotencySnapshot` 的欄位／equality 只包含 accepted-contact effective attack 與 incoming magic power；改變 defender、雙方 act property、projectile-cancel weaken、strength、flight frame 或 facing 不改變 snapshot。
- 固定同一份 incoming potency snapshot，令原始攻擊者暴擊率為 0%、慕容博暴擊率為 100%；回程命中必須使用慕容博的暴擊率與暴擊倍率，同時 base potency 仍等於來襲彈道 snapshot。
- 反向設定原始攻擊者暴擊率為 100%、反射者為 0%；回程命中不得借用原始攻擊者的暴擊率／倍率。
- 令只有反射者具有攻擊性冷卻延長與斬殺條件；回程命中按反射者的機率／延長量與 execute threshold 生效。反向只給原始攻擊者時，回程不得生效。
- 令原始攻擊者的 `HitBeforeDamage` 產生 `ignoreDefensePct`、反射者沒有；原命中可穿防，回程命中不得繼承。
- 令反射者的 `HitBeforeDamage` 產生 `ignoreDefensePct`、原始攻擊者沒有；回程命中必須以反射者的穿防重新計算原始攻擊者防禦。
- 將 incoming `event.skillAttackerActProperty`、慕容博 live act property 與原始攻擊者 live defender act property 設為三個不同值；回程 shaping 必須使用後兩者的差值，證明沒有沿用 incoming field 或 frozen matchup。
- 固定 potency／participants，分別驗證反射點既有 projectile-cancel weaken 會扣減回程傷害、回程中新增的 cancellation 會繼續累積，而 incoming leg 的 elapsed frame 不會進入 potency。
- 以兩個不同回程飛行距離驗證：兩者都從 return `frame = 0` 出發，但較晚命中的回程 leg 依自身 elapsed frame 得到較大 flight decay。
- 所有上述測試同時斷言 return `event.sourceUnitId == reflectorUnitId`、defender 是 original attacker，並以固定 seed 驗證回程暴擊／variance 是獨立 random draw。

### reflected-damage 刪除與資料遷移測試

- 編譯期與 repository search 確認 `BattleDamageKind::Reflected`、`BattleDamageRequest::reflected`、`BattleDamageDefenseInput::reflected`、`DamageChannel::Reflected` 與 `AcceptedHitCondition::excludeReflected` 已無 declaration／reader／writer。
- effect schema／parser 不再接受「排除反彈」；`BattleDamageKind` author／display／matcher 也不再暴露「反彈」、「反射」或 `Reflected` label。
- 現有 `config/chess_*.yaml` 沒有殘留 `排除反彈` 欄位；資料 migration 不需要替 reflected damage-kind label 改寫任何 config，因為現有 config 沒有使用它們。
- `SkillReflectPercent` 仍產生現有普通 direct damage，不偽造 accepted attack provenance，也不被回程彈道的 reflection-lineage 條件誤判。

### 資格政策測試

P01–P15 每一列都必須有：

- 一個正向或負向的明確資格斷言；
- 一個不受 operation type 偶然改寫影響的 descriptor 測試；
- 若該類別可從 effect 複製，至少一個複製後仍保留正確資格的 lineage 測試。

另外固定：

- `static_assert` 驗證 `BattleAttackDelivery`、`BattleProjectilePayloadClass`、descriptor、既有 `BattleAttackPayload` 與 spawn request 均不可 default-construct。
- repository search 確認沒有新增第二個 `BattleAttackPayload` declaration；`HeadlessBattleRunner` 與所有既有 consumer 仍引用原 struct。
- immediate `origin == Reflection` 的 return attack 必須同時具有 `ReflectedReturn` lineage；同一 projectile state 的 continuation clone 不得降級成 `Ordinary`。
- 普通 P07 bounce descendant 依既有 ranged／tracking 規則仍可反射；`ReflectedReturn` lineage 的 P07-shaped bounce descendant 固定不可反射，證明 lineage guard 沒有改變一般 P01–P15 政策。

### 固定隨機與 replay

- 新 replay version 下，固定 seed 的反射率、bounce 與 hit-time 擲骰次數及順序固定；不要求與舊版本 draw order 相同。
- 新的 attack／cast ID、parent lineage、reflection lineage、spawn frame、hit frame 與 finish reason 進入 replay digest。
- GUI 與 headless runner 在同 seed 下產生相同來回軌跡、傷害結果與 debuff 觸發。

## 審查決議

### 已決議

1. 回程 `BattleAttackPotencySnapshot` 只攜帶來襲 accepted contact 的 effective attack 與 magic power；所有透過 live attacker 讀取的 hit-time stats／rules（包括 act property、暴擊、冷卻延長、斬殺、造傷與穿防）由反射者決定。回程 act-property matchup 是 reflector 對 original attacker，不沿用 incoming `skillAttackerActProperty`。
2. `ignoreDefensePct` 不隨 potency snapshot 繼承，回程只使用反射者本次 `HitBeforeDamage` 產生的值。
3. 刪除全部 reflected-damage 舊型別、布林、channel、condition 與「排除反彈」config，不重新指派給 `SkillReflectPercent`。
4. accepted contact 一旦承諾反射，即使原命中殺死反射者，回程彈道仍發射；命中時仍評估死亡反射者的合法 hit rules，包括慕容 debuff。
5. reflection child cast 使用 `magicId = -1`；incoming magic 僅作為 attack payload metadata，原始攻擊者的 magic-bound observer 不得被回程事件觸發。
6. delivery／payload-class／reflection-lineage value types 放在 `BattleAttackDelivery.h`，其中新的分類型別命名為 `BattleProjectilePayloadClass`；既有 `BattleAttackPayload` 保留原名。中央資格放在 `BattleProjectileReflectionPolicy.h/.cpp`；spawn request 的分類與 lineage 無預設、漏填即編譯失敗。
7. dodged contact 不反射，但仍使用 `Normal` settlement 保留現有 bounce／spend 行為。接受 continuation 移動造成的 RNG draw-order 變更，更新 replay version 與新 fixed-seed 基準，不維持舊 replay 相容。
8. `ProjectileReflectChance` 與 `SkillReflectPercent` 沒有互斥：前者產生回程 projectile，後者依承傷產生即時 direct damage；同一 hit 可同時觸發。
9. `ProjectileReflectChance` 以 accepted contact 作為唯一承諾邊界，不等待最終 HP delta；格擋、護盾或承傷上限把原傷害降為 0 時仍可回射。
10. 回程 attack 繼承反射點當下已實體化的 projectile properties 與剩餘 continuation budget，包括 pierce／bounce／retarget；不繼承舊 contact history。累積 projectile-cancel weaken 繼承，return-leg runtime frame 從 0 開始並依自身飛行幀數重新計算 decay。回程及其 continuation clones 固定攜帶 `ReflectedReturn` lineage，所以可以保留原本的 bounce，但整條 lineage 都不能再次反射。

P01–P15 的初始政策已決定為完全保留現況。未來若要重新審查，只修改中央 policy function、本表與對應測試，不將資格特判重新分散到 resolver 或 spawn site。本文目前沒有未決 gameplay 契約；若審查要改變任何決議，應先同步修改正文與測試期望，再開始 implementation。
