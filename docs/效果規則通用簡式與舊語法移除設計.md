# 效果規則通用簡式與舊語法移除設計

狀態：已實作（2026-08-24）。

實作結果：

- 四份正式設定的 424 條規則已全數遷移為 `時機` 與具名 action／condition 語法。
- rule、action、condition 與 `屬性加成.固定` 的舊 reader 已移除；舊外形由正常 parser 邊界直接拒絕。
- `PayloadView` 以 descriptor 統一驗證 duplicate、unknown、required 與 node shape，typed parser 的每次欄位讀取都會記錄消耗；任何合法卻未消耗的欄位會載入失敗。
- action、condition、macro、rule、selector 與 `EffectNumber` 共用 constexpr descriptor；動態屬性 key 使用 canonical `BattleAttribute` label table，所有 enum parser 與 schema completion 也共用 50 組 label descriptors。
- 38 個 payload descriptors 自帶最小合法 probe；220 個 field descriptors 各自帶 probe value 與必要的 alternate context。測試除了確認 14 種 action、25 種 condition 與 11 種 macro 的 typed variant dispatch，也會逐欄走真實 parser 並驗證 supplied fields 全數消耗。
- YAML Schema 產生器直接讀取 C++ payload descriptor 的欄位、必填性、node shape、shared schema reference、nested payload 與 enum label table；四份 checked-in schema 與 VS Code file association 已建立 drift check。repository 沒有 CI，因此 `kys_tests` build script 會一併執行 schema unittest。

本文件接續[《效果規則簡式語法設計》](效果規則簡式語法設計.md)。第一版已證明簡式可以正規化成既有 typed `EffectRule`，但仍把長式保留為複雜規則的正式格式。本階段改變該決策：作者語法只保留一套可完整表達所有效果規則的通用簡式，遷移四份正式效果設定與相關測試後，刪除舊的 rule、action 與 condition 作者語法 parser。

## 目標

完成後必須同時滿足：

1. 四份正式效果設定的 424 條規則全部使用 `時機`，不再出現 rule-level `事件`。
2. 所有 action 都使用具名 action node，不再以 action-level `類型` 選擇 variant。
3. 所有 condition 都使用 scalar、單參數或具名 payload，不再以 condition-level `類型` 選擇 variant。
4. `觀察範圍`、`施放匹配`、`重複次數` 與全部 17 種事件都能由同一套簡式表達。
5. 單一 action 可以提升到 rule；多 action 與巢狀 action list 使用相同具名語法。
6. 封閉意圖巨集仍是可選糖衣，不是完整表達能力的必要條件。任何規則即使不使用巨集，也能用通用簡式精確表示。
7. 遷移完成後直接拒絕舊語法，不加入 legacy mode、格式版本開關或靜默相容 fallback。
8. 正式設定與文件中的 YAML 範例一律使用 block-style map 與 sequence，不使用大括號 flow map。

這裡要移除的是舊的 YAML 作者語法 adapter，不是 typed 效果模型。`EffectRule`、`EffectAction`、`EffectCondition`、`parseActionPayload`、`parseConditionPayload`、selector parser、`EffectNumber` parser、validator、描述器與 runtime 都繼續作為唯一語意實作。

## 非目標與保留邊界

- 不改變任何 event、selector、condition、action 或 rule control 的 runtime 語意。
- 不以武功、羈絆、裝備或內功名稱推斷 payload。
- 不建立可由設定宣告的 template、繼承或變數系統。
- selector、攻擊 runtime 行為及其他 payload 內部 tagged union 仍可保留自己的 `類型` 欄位。本階段刪除的是 rule 的 `事件` 分支，以及 action／condition 外層為了選擇 variant 而存在的 `類型` wrapper；不可用全檔文字取代誤改 payload-level discriminator。
- 不要求每一個進階 action 都變短。通用簡式保證只有一種外形與一條 parser 路徑；語意重要的 payload 欄位仍應明寫。

## 遷移前現況（歷史）

四份正式效果設定共有 424 條規則，其中 381 條已使用 `時機`，43 條仍使用 `事件`：

| 舊事件 | 尚未遷移規則 |
|---|---:|
| `命中傷害前` | 10 |
| `每幀` | 9 |
| `護盾破裂` | 8 |
| `單位死亡` | 6 |
| `友軍死亡` | 4 |
| `施放結算完成` | 2 |
| `絕招冷卻完成` | 2 |
| `攻擊生成` | 1 |
| `施放延續` | 1 |

這 43 條不是 runtime 例外。它們留下來的原因只有第一版作者契約不完整：部分 `時機` 名稱不存在、`每隔` 無法精確表示無間隔的每幀規則，或簡式欄位白名單拒絕 `觀察範圍／施放匹配／重複次數`。

另外，部分已使用 `時機` 的規則仍在 action 或 condition node 內使用 `類型`。因此 rule-level 遷移完成不等於舊 action／condition parser 已可刪除。

## 唯一 rule 外形

最終 rule 只接受下列欄位：

| 欄位 | 必填 | 契約 |
|---|---|---|
| `時機` | 是 | 選擇完整 event，或選擇明確帶自動條件的意圖時機 |
| `觀察範圍` | 否 | 原 `EffectObservationScope`，預設效果擁有者 |
| `施放匹配` | 否 | 原 `EffectCastMatch`，預設綁定武功 |
| `目標` | 否 | 完整 selector；未填時使用時機表的預設 |
| `條件` | 否 | 自動條件之後依 YAML 順序追加 |
| `機率` | 否 | 原 rule chance |
| `次數` | 否 | 原 max activations |
| `同來源冷卻幀數` | 否 | 原 shared cooldown |
| `間隔幀數` | 依時機 | `每隔` 必填，`每幀` 禁止 |
| `每N次事件` | 否 | 原 every-N control |
| `觸發限制` | 否 | 原 activation limit |
| `重複次數` | 否 | 完整 `EffectNumber`，重播整個 action list |
| 一個提升 action | 與 `動作` 二選一 | rule-level 唯一具名 action 或封閉巨集 |
| `動作` | 與提升 action 二選一 | 非空具名 action list |

`觀察範圍／施放匹配／重複次數` 不建立簡式專用 parser。它們解除 rule 欄位白名單限制後，直接呼叫現有 typed 欄位 parser 與 validator。

例如帶進階 wiring 的規則仍是簡式：

```yaml
- 時機: 命中
  觀察範圍: 事件目標
  目標: 自身
  傷害修正:
    方位: 承受
    階段: 防禦後
    傷害種類: 招式
    方式: 百分比加算
    數值: -6
    合併方式: 增加層數
    層數上限: 5
    疊加範圍: 事件來源
```

帶公式重複次數的規則也不再需要長式：

```yaml
- 時機: 單位死亡
  目標:
    類型: 半徑內單位
    半徑格數: 5
    隊伍: 敵方
  條件:
    - 自身有狀態: 毒爆
  重複次數:
    基準: 來源狀態層數
    狀態: 毒爆
    百分比: 100
    最小: 1
  造成傷害:
    數值:
      基準: 來源狀態強度
      狀態: 毒爆
      百分比: 100
    傷害種類: 純粹
    範圍: 單體
```

## 完整時機表

每個 `EffectEvent` 必須有一個不自動加入條件的 lossless 時機名稱。意圖時機是額外捷徑，不能取代 lossless 名稱。

| `時機` | normalized event | 預設目標 | 自動條件 |
|---|---|---|---|
| `開場` | `BattleInitialized` | 自身 | 無 |
| `每幀` | `FrameAdvanced` | 自身 | 無；禁止 `間隔幀數` |
| `每隔` | `FrameAdvanced` | 自身 | 無；必填正值 `間隔幀數` |
| `絕招冷卻完成` | `UltimateCooldownFinished` | 自身 | 無 |
| `施放規劃` | `CastPlanned` | 自身 | 無 |
| `攻擊提交` | `AttackCommitted` | 自身 | 無 |
| `絕招施放` | `UltimateCommitted` | 自身 | 無 |
| `攻擊生成` | `AttackSpawned` | 自身 | 無 |
| `主彈命中` | `MainProjectileBeforeDamage` | 命中目標 | 無 |
| `命中` | `HitBeforeDamage` | 命中目標 | 無 |
| `傷害後` | `DamageResolved` | 自身 | 無 |
| `治療嘗試` | `HealAttempted` | 自身 | 無 |
| `治療套用` | `HealApplied` | 自身 | 無 |
| `施放延續` | `CastContinuation` | 自身 | 無 |
| `施放結算完成` | `CastSettled` | 自身 | 無 |
| `護盾破裂` | `ShieldBroken` | 自身 | 無 |
| `單位死亡` | `UnitDied` | 自身 | 無 |
| `友軍死亡` | `AllyDied` | 自身 | 無 |
| `造成傷害後` | `DamageResolved` | 自身 | 傷害方位＝造成、已接受命中 |
| `受傷後` | `DamageResolved` | 自身 | 傷害方位＝承受、已接受命中 |
| `擊殺後` | `DamageResolved` | 自身 | 傷害方位＝造成、傷害造成死亡 |

`每幀` 與 `每隔` 必須分開。把每幀規則機械補成間隔一幀雖然可能有相同 runtime 結果，卻不是相同 normalized rule，也會污染描述、內容指紋與欄位級遷移證據。

這項區分必須在 `parseTiming` 保留作者時機名稱時立即驗證，不能只依賴 `validateEffectRule`。現有 validator 只知道 normalized event 與 interval 數值，因此無法區分作者寫的是 `每幀` 或 `每隔`：

- `時機: 每幀` 只允許沒有 `間隔幀數`，出現該欄位即載入失敗。
- `時機: 每隔` 必須具有正值 `間隔幀數`，缺少、零值或負值都載入失敗。
- 兩種正反形狀都要有 timing parser 單元測試；不能把它列為既有 validator 已涵蓋的行為。

除 `主彈命中／命中` 外，lossless 時機一律預設自身。這避免新增未經驗證的目標推斷；治療事件若要操作交易目標，作者必須明寫 `目標: 交易目標`。第一輪機械遷移保留所有原本明寫的 `目標`，只有在 normalized equality 已確認後才可另做省略目標的可讀性整理。

來源 loader 限制仍在正規化後由同一 validator 執行。例如絕招效果設定仍不可使用 `開場`；完整時機表不代表每個來源都允許每個 event。

## 所有 action 使用具名 node

通用規則是：action node 必須是只有一個 action 名稱的 map，value 是該 action 的 canonical payload。名稱直接傳入 shared `parseActionPayload`，不合成人工 YAML，也不維護第二份 payload parser。

所有 14 個 canonical action variant 都必須支援此形式：

| 具名 action |
|---|
| `屬性修正` |
| `傷害修正` |
| `資源變更` |
| `治療交易修正` |
| `套用狀態` |
| `消耗狀態` |
| `移除狀態` |
| `造成傷害` |
| `修改攻擊` |
| `強制移動` |
| `建立區域` |
| `修改施放` |
| `狀態機` |
| `條件分支` |

封閉巨集與意圖 action，例如 `回復生命／屬性加成／擊退`，與這 14 個 lossless 名稱共用作者名稱空間，但使用獨立的 macro registry。lossless action registry 必須完整覆蓋 `EffectActionValue`，不能再由一份手寫 label 白名單與一串獨立 dispatch 分支碰巧保持同步。

### 機械化 registry 完整性

作者語法以 constexpr descriptor 作為單一名稱來源：

- 每個 lossless action descriptor 包含唯一作者名稱、對應 `EffectActionValue` variant index 與 payload kind。
- action 名稱查找、payload dispatch、具名 action schema 生成及測試 case 列舉都讀取同一份 descriptor 表。
- 編譯期檢查 descriptor 數量等於 `EffectActionValue` alternative 數量、每個 variant index 恰出現一次、名稱唯一，且不與 rule 欄位或 macro 名稱碰撞。
- macro descriptor 另列名稱與展開函式，因為一個 macro 可以產生多個 action，不能拿來填補 lossless variant coverage。

condition 使用相同機制：每個 descriptor 包含唯一名稱、`EffectCondition` variant index、允許的作者外形，以及單參數時的 canonical 欄位名稱與 value shape。`已接受命中` 可同時宣告 scalar default 與多參數 payload；每個 condition variant 仍只能有一個 descriptor。編譯期檢查完整覆蓋所有 `EffectCondition` alternatives，schema 測試再遍歷 descriptor，確認每個 variant 都能由作者語法進入 shared payload dispatch。

屬性名稱、rule 保留欄位、action 名稱、macro 名稱與 condition 名稱也要各自檢查唯一性；需要互斥的名稱空間以 compile-time assertion 固定，不只在文件宣告意圖。

### Payload 欄位也是單一來源

名稱 registry 完整仍不足以保證 schema 與 parser 一致。每個 payload kind 的 descriptor 必須同時列出欄位名稱、required／optional、允許的 YAML node shape、scalar type 或共用 schema reference，以及 enum 欄位使用的 label table。

parser 自己使用這份欄位 metadata：

- dispatch 找到 payload descriptor 後，先以 descriptor 驗證 duplicate、unknown、required 與 coarse node shape。
- typed payload parser 只接收 descriptor-backed `PayloadView`，不直接持有原始 map；所有欄位讀取都透過 view，並標記 supplied field 已消費。
- typed branch 不再保留自己的 `validateKnownKeys` literal。跨欄位條件、數值範圍與 typed constructor 邏輯仍留在 branch，但 allowed field set 不可重複宣告。
- supplied field 若在 shape gate 合法、卻沒有被 typed branch 消費，payload parse 失敗。這會抓到 descriptor 新增欄位但 parser 忘記處理的反向 drift。
- nested selector、number、action list 或 condition list 在 parent view 取出 node 後，交給各自 descriptor-backed parser；parent field 視為已消費，nested map 再檢查自己的欄位。

schema generator 讀取同一份 payload field descriptors，因此 parser 接受的欄位、editor completion 與 generated schema 沒有第二份手抄 whitelist。複雜語意仍由 typed parser／validator 補充，不嘗試把全部 runtime invariant 塞進 schema。

合法 probe data 也屬於 descriptor metadata，不能另建約 150 筆 test-only field table：

- 每個 payload descriptor 提供一個最小合法 probe payload。
- 每個 field descriptor 提供合法 probe value；若該欄位與最小 payload 的其他欄位互斥，另指定同一 payload descriptor 內的 named probe context，再套用 probe value。
- nested payload 的 probe value 優先 reference 另一個 payload descriptor 的最小合法 payload。例如 `消耗狀態.最後一層` reference `套用狀態`，不複製第二份巢狀範例。
- probe sample 是作者語法測試／schema example metadata，不是 runtime default，parser 不可用它補齊缺少欄位。
- schema generator 可選擇將最小合法 payload 與適合展示的 field samples 輸出為 editor examples；測試則必須使用全部 samples。

測試遍歷每個 payload descriptor，由最小合法 payload 或 field 指定的 probe context 出發，逐一套用 declared field 的 probe value，呼叫真實 payload parser，並斷言成功且 supplied fields 全部被消費。這同時覆蓋 field-list completeness；只測 variant 可抵達 dispatch 不算完成。

### 動態 key payload

`屬性加成` 不是 closed field map：除保留的 `百分比` 與 qualifier 外，其他 key 由 canonical `BattleAttribute` label class 決定。不可為了套用 closed-field descriptor 而把所有屬性複製成巨集欄位列表。

macro descriptor 因此可宣告 dynamic key class：

- key class reference 共用的 enum label table，例如 `BattleAttribute`。
- value shape，例如 scalar number。
- reserved closed fields，例如 `百分比` 與 qualifier；reserved fields 仍使用一般 field descriptors。
- normalized uniqueness、最少項目數與 dynamic key 展開順序。
- dynamic key 的 probe 由 key-class descriptor 提供一個代表 label 與 value，不另建 macro test table。

`PayloadView` 對 closed field 提供具名讀取，對 dynamic key class 提供經分類的 entry range；macro parser 迭代該 range 時標記 entry 已消費。unknown key、未消費 dynamic entry 與解析後 enum 重複都必須失敗。未來若有其他 key-class map，也必須明確宣告 dynamic descriptor，不能繞過共同 shape gate。

複合及巢狀 action 不再回到舊語法：

```yaml
- 時機: 主彈命中
  動作:
    - 消耗狀態:
        狀態: 七星
        層數: 1
        狀態來源: 效果擁有者
        最後一層:
          套用狀態:
            狀態: 眩暈
            持續幀數: 30
    - 傷害修正:
        方位: 造成
        階段: 防禦前
        傷害種類: 招式
        方式: 忽略防禦百分比
        數值: 50
```

條件分支也使用相同 action-list parser：

```yaml
- 條件分支:
    條件:
      - 自身生命低於: 30
    成立:
      - 回復內力: 20
    否則:
      - 獲得護盾:
          來源最大生命百分比: 5
```

像素級 `擊退／拉近` 放在 `條件分支` 內仍是不合法的 exact-runtime composition。頂層意圖 action 可以提供較具體的作者錯誤；巢狀違規由遞迴的通用 validator 回報精確 runtime 動作不可放在條件分支內即可，不要求再維護一份遞迴 shorthand-only 檢查。

## 所有 condition 使用具名語法

condition 依 payload 形狀分成三種作者外形，但全部進入同一 `parseConditionPayload`：

1. 無參數 condition 使用 scalar。
2. 恰有一個參數的 condition 使用 condition 名稱對應原 value，可接受 scalar 或 sequence。
3. 多參數 condition 使用 condition 名稱對應 payload map。

```yaml
條件:
  - 僅限主彈道
  - 自身生命低於: 30
  - 傷害種類符合:
      - 招式
      - 特效
  - 已接受命中:
      需要正傷害: true
      排除反彈: true
  - 自身層數至少:
      狀態: 戰意
      層數: 2
```

`已接受命中` 在兩個欄位都採預設時仍可寫 scalar；只要覆寫任一欄位，就使用上面的具名 payload map。`自身層數至少` 固定使用具名 payload map。未知 condition、錯誤外形及未知 payload 欄位都必須失敗。

時機自動條件仍先於作者條件。作者新增與自動條件相同的 condition variant 時載入失敗；需要自訂該條件時，改用 lossless `傷害後` 並明寫完整條件，不做隱式合併。

## 全域重複 key 契約

重複 YAML map key 幾乎一定是作者錯誤，不應只在 `屬性加成` 嚴格拒絕。統一 parser 將 raw key 唯一性提升為所有 map 的共同邊界：

- `validateKnownKeys` 在檢查 unknown field 前先迭代原始 map entry，以字串 key 集合拒絕重複 key。
- 不使用 `validateKnownKeys` 的 map parser 必須先呼叫同一個 `validateUniqueKeys` helper；rule、selector、number、action、condition、巢狀 payload 與 macro 不得例外。
- 診斷指出重複 key 與所在作者 node，不依賴 yaml-cpp 的 key lookup 結果。
- raw key 唯一性不能取代 domain-level 唯一性。例如兩個不同屬性別名若解析成同一個 `BattleAttribute`，`屬性加成` 仍須以 normalized attribute 集合拒絕。
- 每個主要 map family 至少有一個 duplicate-key rejection test；不為每個 action 複製相同測試。

YAML／JSON Schema 通常只能看到 loader 產生的 map，不能可靠證明原始 YAML 沒有重複 key；此規則以原生 YAML parser 邊界為準。

## 更扁平的 `屬性加成`

第一版 `屬性加成` 把固定加算再包在 `固定` map 中。固定加算是最常見且最自然的預設，因此最終語法改為：直接位於 `屬性加成` 下的 canonical 屬性名稱代表固定加算，只有百分比加算保留 `百分比` 分組。

```yaml
- 時機: 絕招施放
  屬性加成:
    攻擊: 50
    防禦: 30
    百分比:
      速度: 15
    持續幀數: 100
```

正規化結果為同一條 rule 內的三個 `ModifyAttributeAction`：

1. 攻擊固定加算 50。
2. 防禦固定加算 30。
3. 速度百分比加算 15。

`持續幀數` 以及其他共用 qualifier 複製到全部生成 action。完整封閉契約如下：

- 直接屬性 key 必須是現有 canonical `BattleAttribute` 名稱，value 必須是 scalar 數字，operation 固定為固定加算。
- `百分比` 存在時必須是非空 map；內層 key 是 canonical 屬性名稱，value 是 scalar 數字，operation 固定為百分比加算。
- 共用 qualifier 只接受 `持續幀數／合併方式／層數上限／每層／疊加範圍`。
- 除 `百分比` 與五個 qualifier 外，其餘 key 一律當成屬性名稱解析；未知名稱直接失敗。
- 至少需要一個直接屬性或一個百分比屬性，只有 qualifier 的 node 不合法。
- 同一直接屬性不可重複，同一百分比屬性不可重複，同一屬性也不可同時出現在直接區與 `百分比`。
- `屬性加成` 外層與 `百分比` 內層的 raw key 唯一性由全域 map 契約處理；macro 另以 normalized `BattleAttribute` 集合拒絕跨別名及跨固定／百分比重複。
- parser 保留字、qualifier 名稱與 canonical 屬性名稱必須是互斥集合；未來新增屬性或 qualifier 造成名稱碰撞時，schema 測試必須失敗。
- 展開順序固定為直接固定加算在前、百分比加算在後；各組依 canonical `BattleAttribute` 順序。不得依賴 YAML 輸入順序。
- `固定` wrapper 不屬於最終語法。現有第一版寫法在同一批遷移中改成直接屬性，parser 隨後刪除 `固定` 分支。
- 公式數值、覆寫、乘算、至少為，或不同屬性需要不同 qualifier 時，使用具名 `屬性修正`。不為了縮短而隱藏語意。
- 合併多個既有 action 時，只有在巨集展開順序與原 action 順序一致時才可合併；否則保留多個具名 `屬性修正` 或拆成多個 action node，避免遷移改變 action settlement 順序。

單一固定屬性也使用同一形式：

```yaml
- 時機: 開場
  屬性加成:
    防禦: 50
```

百分比單一屬性寫成：

```yaml
- 時機: 開場
  屬性加成:
    百分比:
      攻擊: 20
```

## YAML Schema 編輯支援

應提供 YAML Schema，目的只是在編輯設定時提供 completion、欄位文件與即時 structural validation。它不是 runtime 語意的第二個權威實作，也不新增 standalone config-check executable；真正的 runtime 驗證仍由正常啟動遊戲時使用的 content loader、parser 與 validator 負責。

### 產生的 schema

建議提交四個對應頂層檔案外形的 JSON Schema 相容 YAML schema，並共用效果 rule、selector、condition、action、number 與 macro definitions：

- `schemas/chess_effects/chess_combos.schema.json`
- `schemas/chess_effects/chess_equipment.schema.json`
- `schemas/chess_effects/chess_magic_effects.schema.json`
- `schemas/chess_effects/chess_neigong.schema.json`

schema 刻意放在 `config` 之外，避免一般 asset copy 把 editor metadata 帶進 build output。若未來 build 改為複製整個 repository，再明確排除 `schemas` 即可。

`.vscode/extensions.json` 推薦 `redhat.vscode-yaml`，`.vscode/settings.json` 以 `yaml.schemas` 將四份正式設定各自綁定對應 schema，不要求在設定檔加入 modeline。schema 至少提供：

- 欄位名稱、required field、scalar／map／sequence shape 與 unknown-field rejection。
- 完整 `時機`、selector、action、condition、attribute、status 及 enum label completion。
- action node 恰有一個具名 action、condition 的三種作者外形，以及 rule 提升 action 與 `動作` 的互斥。
- `每幀` 禁止 interval、`每隔` 必填正 interval 等可由 schema 明確表示的條件。
- 扁平 `屬性加成` 的直接 canonical 屬性、`百分比` 與 qualifier 封閉欄位。

rule 提升 action 恰有一個，以及提升 action 與 `動作` 二選一，會由 closed action-name set 產生 `oneOf`／排除條件。YAML Language Server 對這類 XOR 違規通常只顯示一般化的 `oneOf` 診斷，不保證能說明「同時寫了兩個提升 action」。這是 editor convenience 的已知限制，不是 schema 漂移；正常遊戲 parser 仍提供具體作者錯誤。

schema 不手寫另一份 action／condition 名稱清單。作者語法 descriptor 除 dispatch metadata 外，也提供 schema 所需的欄位 shape metadata；schema generator 由同一份 descriptors 與 enum label tables 產生檔案。產生結果可以提交，讓 editor 不必先 build；CI 重新產生到暫存位置並比較 checked-in schema，發生 drift 即失敗。

複雜 payload 的跨欄位語意仍由原生 validator 負責。若某項限制無法合理由 descriptor 產生，就不要在手寫 schema 複製一份容易漂移的規則。Schema 不承諾驗證重複原始 key、loader-specific event 限制、runtime capability、exact-runtime composition、跨檔 reference、macro normalized ordering 或內容指紋；這些在正常遊戲載入時由現有 parser 與 validator 檢查。

unit tests 只負責 descriptor coverage、schema generation drift、正反 shape 及 parser／validator 實作回歸。設定作者的日常流程是編輯時使用 schema，完成後正常啟動遊戲確認 runtime，不增加另一個執行入口。

## Parser 收斂與刪除範圍

最終 parser 流程為：

```text
唯一作者 rule
  → parseTiming
  → parseRuleControls
  → parseSelector
  → parseAuthorConditions
      → parseConditionPayload
  → parseAuthorActions
      → parseActionPayload
  → validateEffectRule
  → typed EffectRule
```

完成遷移後刪除：

- `事件` 與 `時機` 的雙分支，以及 `simplified` 狀態判斷。
- canonical rule 欄位白名單與長短式混用診斷；只保留唯一 rule 欄位白名單。
- action node 讀取外層 `類型` 的 wrapper。
- condition node 讀取外層 `類型` 的 `Canonical` form。
- 只覆蓋部分 action 的手寫 named-action 白名單；改為涵蓋所有 variant 的單一 action registry。
- `屬性加成` 的 `固定` wrapper parser。
- 只為舊 YAML fixture 存在的 parser 測試與 helper。

保留並共用：

- `parseActionPayload` 及每個 action 的欄位 parser 與 typed constructor。
- `parseConditionPayload` 及每個 condition 的欄位 parser 與 typed constructor。
- selector、number、status、stack、area、attack、cast 與 state-machine payload parser。
- `validateEffectRule`、描述與內容指紋。

此處「保留並共用」只代表 typed 語意、constructor 與跨欄位規則繼續存在，不代表 parser 內部不改。導入 descriptor-backed `PayloadView` 會重寫約 30 個 payload parsers 的欄位存取與 map 邊界；這是本計畫的主要工程成本。

### PayloadView 基礎重構 checkpoint

這項基礎重構必須先成為獨立 checkpoint，再讓後續通用語法與 schema 依賴它：

1. 先盤點所有 closed-field 與 dynamic-key payload，建立 field descriptors、probe metadata 與 key-class descriptors。
2. 實作共同 duplicate／unknown／required／shape gate、consumption tracking 與 `PayloadView`。
3. 分類機械遷移 selector、number、condition、action 及 nested payload 的 raw node access；此時不改作者語法或 typed normalized 結果。
4. 以現有正式設定完整載入、descriptor probe tests 與完整 unit-test batch 驗證一次，並對 field-access architecture 做一次集中 code review。
5. checkpoint 通過後，才補齊 universal timing、named forms、schema generation 與設定遷移；不得讓後續批次一邊依賴、一邊繼續改寫 PayloadView 基礎契約。

不得保留舊 reader 作為「相容投影」。專案規則要求移除 backwards compatibility；正式設定與測試遷移完成後，舊語法應成為 unknown field 或 invalid node shape。

## 完整遷移計畫

### 第一批 A：PayloadView 與 descriptor 基礎

1. 建立 action／condition／payload field／dynamic key-class descriptors，以及 descriptor-owned probe data。
2. 實作 `PayloadView`、field consumption tracking 與共同 map shape gate。
3. 將約 30 個 payload parsers 的 field whitelist 與 raw node access 遷移到 descriptors／view，保留現有作者語法與 normalized typed 結果。
4. 將 raw duplicate-key rejection 下沉到所有 map parser 的共同邊界。
5. 完成基礎重構 checkpoint 的集中 review、正式設定載入與一次完整 unit-test batch。

### 第一批 B：補齊 lossless 語法與 editor schema

1. 加入完整時機表，特別分開 `每幀` 與 `每隔`。
2. 將 `觀察範圍／施放匹配／重複次數` 加入唯一 rule schema。
3. 讓全部 action／condition variants 由 single-key registry 完整覆蓋，並加入多參數 condition 的具名 payload form。
4. 實作扁平 `屬性加成`，以 dynamic `BattleAttribute` key class 表達直接固定加算。
5. 由同一份 descriptors 產生 YAML Schema，供 editor completion 與 structural validation。

第一批 B 先增加新路徑並以欄位級對照測試固定 normalized 結果，尚不宣告完成。它只描述同一實作分支內的工作順序；不得把雙 parser 狀態當成可交付終點。

### 一次性逐規則遷移 verifier

在舊 parser 仍存在且正式設定尚未改寫時，記錄包含四份遷移前設定的 immutable git commit hash，建立只服務本次遷移的 old-vs-new verifier。verifier 執行時由該 git ref 將四個檔案 materialize 到 temporary directory，不把 baseline 副本加入 repository：

1. 舊檔走 `事件` 與外層 `類型` 路徑，新檔走 `時機` 與具名 node 路徑。
2. 以來源檔、definition identity、效果區段與作者 rule ordinal 建立穩定配對；本次純語法遷移禁止一拆多或多併一，因此必須恰有 424 對。
3. 每一對直接使用現有 test-side deep structural comparator，比較 event、observation、cast match、selector 全欄位、condition payload、rule controls、activation limit、repetition formula、全部 action payload 與巢狀 action。
4. `Full` 與 `Compact` 描述相等、rule ID 相等及整體內容指紋相等作為額外證據，不拿描述或指紋取代 structural equality。
5. 失敗訊息至少指出來源 identity、rule ordinal 與第一個不同的 typed field path，讓漂移可直接定位。

這個 verifier 只證明目前 canonical 作者 YAML 到通用簡式 YAML 的一對一改寫；它不重建已刪除的早期效果系統，也不是重新要求不可行的 367 條 legacy runtime oracle。第四批與舊 parser 一起刪除 pinned ref、materialization code 與 verifier，最終產品不保留 baseline 檔或相容層。

### 第二批：一次遷移四份正式設定

遷移範圍固定為頂層：

- `config/chess_combos.yaml`
- `config/chess_equipment.yaml`
- `config/chess_magic_effects.yaml`
- `config/chess_neigong.yaml`

機械遷移規則：

1. 43 個 `事件` rule 依完整時機表轉為 `時機`。
2. 無 `間隔幀數` 的 `每幀` 轉為 `時機: 每幀`；有正間隔的週期 rule 使用 `時機: 每隔`。
3. 原本的 `觀察範圍／施放匹配／重複次數／目標／控制欄位` 原樣保留，不依時機猜測或刪除。converter 必須先解析舊 rule 的 effective selector；若舊 rule 省略 `目標` 而新 `時機` 預設不同，就在新 rule materialize 舊 selector。特別是舊 `命中傷害前／主彈道命中傷害前` 未填目標時代表自身，轉成預設命中目標的 `命中／主彈命中` 時必須明寫 `目標: 自身`。
4. action-level `類型` node 改為具名 action node；包含條件分支內、狀態耗盡後及其他巢狀 action list。
5. condition-level `類型` node 改為 scalar、單參數或具名 payload。
6. 所有 `屬性修正` 保留為一對一具名 action，不在本批合併或改寫成 `屬性加成`。使用 named lossless action 已符合唯一簡式，macro adoption 不是舊 parser 移除條件。
7. 其他 action 保留完整 payload，只移除外層結構噪音。
8. 第一輪保留所有明寫目標。省略等於預設的目標屬於後續純可讀性批次，不與語法遷移混在一起。
9. 新增或改寫的 YAML map 與 sequence 全部使用 block style；converter 不輸出 flow-style map。
10. 每完成一份設定立即執行一次性逐規則 verifier；四份完成後再檢查整體內容指紋。

轉換必須依 YAML node context 進行，禁止全檔搜尋取代 `類型`，因為 selector 與 payload 內仍有合法 discriminator。

### 第三批：遷移測試、文件與產生器

- 所有 YAML 測試 fixture 改用唯一作者語法；需要直接建立特殊 typed rule 的測試改用 typed builder，不保留舊 parser 只為測試服務。
- 更新效果設計文件與範例，將第一版長式視為歷史背景，不再呈現為可用格式。
- 設定產生器與轉換腳本只輸出唯一作者語法。
- 提交產生的四份 YAML Schema、`.vscode/settings.json` 的 `yaml.schemas` file associations、`.vscode/extensions.json` 的 `redhat.vscode-yaml` recommendation，以及 schema drift check。
- 頂層正式設定以外的 build-copy assets 不手動遷移，繼續由既有 build copy 流程產生。

### 第四批：刪除舊 parser

- 移除 rule `事件` reader。
- 移除 action／condition 外層 `類型` reader。
- 移除 `屬性加成.固定` reader。
- 移除只服務舊格式的錯誤訊息、分支、pinned baseline ref、git materialization code 與一次性逐規則 verifier。
- 不提供過渡 flag；舊語法立即載入失敗。

### 第五批：獨立可讀性整理

舊 parser 已刪除並完成 universal migration 後，才另開可讀性批次：

- 將合適的 scalar 固定／百分比 `屬性修正` 改為扁平 `屬性加成`。
- 只有相同 qualifier 且巨集展開順序與原 action 順序完全一致的相鄰 action 才可合併；其餘維持一對一 action。
- 省略確實等於時機預設的明寫目標。
- 每個可讀性批次獨立檢查 typed rules、內容指紋與完整設定載入，不與舊語法移除混在一起。

## 驗證與完成條件

驗證以語法家族與整批內容為單位，不建立每一招 runtime scenario：

1. 每個 lossless 時機各有 normalized event、default target 與 auto-condition 對照；`每幀` 帶 interval 及 `每隔` 缺少或使用非正 interval 都有 parser-level rejection test。
2. action／condition descriptor 具有 compile-time 數量、variant index coverage、名稱唯一與名稱空間互斥檢查；測試遍歷 registry，證明每個 variant 可由作者語法抵達 shared dispatch。
3. payload field descriptors 驅動 parser 的 duplicate、unknown、required 與 shape gate；測試完全由 descriptor-owned 最小 payload、field probe value 與必要的 named probe context 產生，逐欄斷言真實 parser 接受且 supplied fields 全部被消費，不另維護 test probe table。
4. 每個 action variant 各有 typed payload 對照，確認具名 wrapper 只改變作者外形。
5. 每個 condition 外形各有欄位級對照；多參數 condition、sequence condition 與未知欄位都有正反測試。
6. rule、action、condition、number、selector、巢狀 payload 與 macro map 各有代表性的 duplicate raw-key rejection；扁平 `屬性加成` 另測 normalized attribute 重複。
7. 扁平 `屬性加成` 對照 action 數量、順序、operation、數值與全部共用 qualifier；未知 key、空內容及跨固定／百分比重複都必須失敗。
8. 一次性 verifier 由 pinned git commit materialize baseline，對 424 對 normalized rules 執行 deep structural equality，並回報可定位的 source／ordinal／field path。整體內容指紋相等是額外 batch gate，不取代逐規則比較。
9. checked-in YAML Schema 必須等於 descriptor generator 的最新輸出，並能在 editor 中套用到四份正式設定，提供 completion 與 structural diagnostics。
10. 四份正式設定完整載入，並執行一次完整 unit-test batch。
11. 舊 parser 刪除前，暫時的 migration traversal audit 以 YAML node context 確認 rule 不再有 `事件`、action／condition 外層不再有 `類型`、`屬性加成` 不再有 `固定` wrapper。它只走 `動作／成立／否則／最後一層` 等已知 action list 與 rule node，禁止文字匹配；舊 parser 刪除後由正常載入失敗與 rejection tests 取代，audit 可一併刪除。
12. 對舊 rule、舊 action、舊 condition 與舊 `屬性加成.固定` 各保留一個 rejection test，證明舊 parser 已移除，而不是仍在 fallback。

只有在新語法完整覆蓋、424 對逐規則 structural equality 通過、四份設定與測試全部遷移、generated schema 無 drift、舊 reader 已刪除且內容指紋不變後，這個階段才算完成。只讓 424 條規則都能載入，但仍保留雙 parser，不算完成；第五批 macro 可讀性整理不是舊 parser 移除的完成門檻。
