# 效果設定差分遷移設計

## 目的

367 個目前啟用的效果條目不能靠人工抄表證明「沒有值遺失」。遷移期間以舊 parser 作為唯讀 oracle，讓舊設定與新設定各自解析成同一份 canonical semantics，再逐來源、逐條目做機械差分。

舊 parser 只在遷移測試 target 存活。所有設定完成且差分通過後，刪除舊正式 parser、舊 enum 及 oracle adapter；不保留 runtime 相容層。

第一階段先把三份遷移前設定複製到暫時的 `tests/fixtures/effect_migration_v1/`。第二階段的新格式也先放在暫時的 v2 fixture，不讓尚未有 executor 的 schema 取代遊戲正在使用的 top-level config。第三階段按機制族同時切換 top-level config 與 runtime consumer；全部切換後刪除 v1／v2 暫存、舊 parser 與 oracle adapter。

## 遷移範圍

| 來源 | 現有條目數 | 遷移結果 |
|---|---:|---|
| `config/chess_combos.yaml` | 212 | 戰鬥規則進入共用 schema；非戰鬥資料移回羈絆／商店領域 |
| `config/chess_equipment.yaml` | 130 | 戰鬥規則進入共用 schema；裝備 metadata 保留在裝備領域 |
| `config/chess_neigong.yaml` | 25 | 戰鬥規則進入共用 schema |

停用的 `config/chess_magic_effects.yaml` 不屬於「舊行為等價」的 367 條；它使用新 schema 實作 59 招，另由單招場景驗證。

## Canonical semantics

canonical 表示執行所需的完整語意，不保留舊欄位名稱，也不保存顯示文字：

```cpp
struct CanonicalEffectSource
{
    EffectSourceKind kind{};
    int sourceId{};
    int sourceLevel{};
    int originalEntryIndex{};
};

struct CanonicalEffectRule
{
    CanonicalEffectSource source{};
    EffectEvent event{};
    EffectSelector selector{};
    std::vector<EffectCondition> conditions;
    int chancePct{};
    int maxActivations{};
    ActivationGroupId activationGroup{};
    std::vector<CanonicalEffectAction> orderedActions;
    RuntimeOrderingKey ordering{};
};
```

canonical equality 必須比較：

- 事件、來源、目標、條件；
- 每一次機率判定的值、順序與共享／獨立關係；
- 啟用次數、計時、層數及逐目標 runtime key；
- action 順序、數值公式、取整、持續、上限及合併方式；
- 選擇排序、平手規則、隨機來源；
- 傷害／治療／狀態的結算階段；
- runtime 與 presentation 所需的 semantic source ID；
- 舊規則在不同 phase 暗中被讀取多次的行為。

不比較舊 `text`、新 localization label、YAML 欄位順序或記憶體位址。

## 正規化舊 parser

舊 parser 輸出 `ComboEffect` 後，oracle adapter 必須把所有隱含語意顯式化，不能只逐欄轉抄：

| 舊行為 | canonical 正規化 |
|---|---|
| `ProjectileBounce` 強制 `OnHit` | event 明確設為命中，不保留原始空 trigger |
| `OffensiveCharm` 產生 `CharmCDRDebuff` | 展開為具 ordering 與 activation coupling 的兩個 canonical action／rule；依現況判斷共享或獨立亂數及計數 |
| 擊退未填距離／鎖定 | 填入距離 5、鎖定 3 幀 |
| 附近追蹤彈未填傷害 | 填入目前隱含的 40% |
| 遠程最低距離未填 | 填入 6 格 |
| 流血未填層數上限 | 填入 5 層 |
| deprecated `ArmorPen*` | 轉為相同事件、機率與穿防比例，不因名稱統一而合併判定 |
| 同一效果被不同 runtime phase 查詢 | 每個 phase 形成明確 canonical consumer，保留現有事件順序 |

任何在 C++ switch 中發現的新隱含值，都必須先新增 oracle normalization test，再遷移對應設定。禁止在新 parser 也複製隱含預設來讓測試「剛好相等」；新 YAML 應明寫會影響行為的值，或由新 schema 唯一且有文件的預設提供。

## 差分管線

```text
舊 YAML ──舊 parser── oracle normalization ──┐
                                             ├── canonical equality
新 YAML ──新 parser── schema normalization ──┘
```

測試流程：

1. 以 `(sourceKind, sourceId, level, originalEntryIndex)` 建立舊條目的穩定 key。
2. 舊 parser 解析唯讀 v1 fixture，oracle 將結果正規化並寫入記憶體。
3. 新 parser 解析 v2 fixture／已切換的 top-level 節點。預設按同來源的原始條目順序對應；只有一拆多、多併一及跨領域 relocation 使用暫時的 test-side exception map。exception map 不進正式 YAML 或 runtime schema。
4. 對每個 key 比較 canonical rules，多規則來源按 `RuntimeOrderingKey` 比較，不能先排序成看似相同的集合。
5. 額外比較每個來源的條目數、規則數、activation group 數及非戰鬥 relocation 數。
6. 全部相等後才允許刪除該批舊設定欄位。

若一條舊規則被新 schema 拆為多條，或多條舊規則合併成一條，只有在 canonical activation、ordering 及 runtime key 仍完全相同時才可等價。單看最終數值相同不足以通過。

## 非戰鬥效果 relocation

金幣、免費刷新、戰場選擇及計作羈絆不應偽裝成戰鬥 action，但移出 dispatcher 也不能跳過差分。canonical 使用領域事件表示：

```cpp
using CanonicalConfiguredBehavior = std::variant<
    CanonicalEffectRule,
    CanonicalEconomyRule,
    CanonicalShopRule,
    CanonicalFormationRule>;
```

舊端由 `EffectType` 正規化成對應領域規則，新端由新的 typed config 解析。比較其來源、條件、數值、上限與啟用時機。完成後 battle schema 中不得保留空殼 action 只為通過 migration。

## Description 差分的角色

舊描述有格式錯誤、隱含值及歷史用語，不能作為新語意的 oracle。遷移門檻分開判斷：

- canonical equality 證明執行語意和值沒有遺失；
- 新描述 golden 證明繁體中文輸出符合[效果描述語法設計](效果描述語法設計.md)；
- 數值 mutation test 證明描述與 payload 沒有分叉。

不得為了讓舊／新字串相同而保留舊描述 switch。

## 行為差分補強

parser canonical 相等仍不能取代 battle regression。每一批遷移還要在舊執行器與新執行器之間比較固定種子 trace：

```cpp
struct EffectExecutionTrace
{
    int frame{};
    EffectSourceBinding source{};
    EffectEvent event{};
    int sourceUnitId{};
    std::vector<int> selectedTargetIds;
    std::vector<int> randomDraws;
    std::vector<CanonicalGameplayCommand> commands;
    CanonicalRuntimeDelta runtimeDelta{};
};
```

差分必須保持：

- random draw 的次數、值與相對順序；
- target ID 及平手順序；
- 命令順序、取整及來源歸屬；
- activation count、timer、stack、pending state；
- 固定種子 battle digest、最終 runtime 及總幀數。

內容指紋與 replay schema 因 YAML 結構改變可明確更新；遊戲行為、亂數順序與總幀數不可藉機簡化。

## 分批策略

每批以機制族群切分，不以檔案整包切換：

1. 常駐固定／百分比屬性。
2. 命中與施放觸發的資源、狀態。
3. 機率、次數及逐目標 runtime。
4. 彈道、反彈、位移及死亡效果。
5. 非戰鬥領域 relocation。

第二階段先在 v1／v2 fixtures 完成 parser canonical 差分與描述測試，不更換遊戲讀取的 top-level config。第三階段每批依序進行：把已驗證 v2 節點提升到 top-level → 同一批替換 runtime consumer → canonical 與 execution trace 雙差分 → 刪除該族舊正式分支。階段結束時不能留下「新 parser、舊 executor」或反向混搭的永久路徑。

## Oracle 刪除門檻

滿足以下條件後刪除舊 parser oracle：

- 367／367 個舊條目都有穩定 key 且 canonical equality 通過；
- 所有隱含預設與暗中 expansion 都已有具名 fixture；
- 非戰鬥 relocation 逐條通過；
- 全部行為 trace、fixed-seed digest 與最終 runtime 通過；
- 新描述 variant 覆蓋與 mutation test 通過；
- repository 搜尋不再有正式 `ComboEffect`／舊 `EffectType` consumer；
- 暫時的 v1／v2 YAML fixture 與 split／relocation exception map 已刪除。

刪除 oracle 後保留 canonical fixtures、schema validator tests、description tests 及 fixed-seed regression。fixtures 是新系統的行為契約，不是舊格式相容層。
