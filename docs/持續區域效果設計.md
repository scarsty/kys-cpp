# 持續區域效果設計

## 目的與最小邊界

目前沒有持有持續戰場區域的 owner。黃沙萬里鞭需要固定沙暴，伏魔杖法需要跟隨施法者的光環；若把 timer 與半徑複製到每個受影響單位，離開範圍、來源死亡與重疊規則都會分叉。

本設計只新增一個由 `BattleRuntimeState` 持有的 `BattleAreaEffectState`、一組建立／到期命令與純查詢 API。不建立通用場景 entity hierarchy，不把即時 5×5 傷害或普通目標選擇硬塞成持續區域。

## Runtime schema

```cpp
using BattleAreaId = StrongId<struct BattleAreaIdTag>;

enum class BattleAreaShape
{
    Circle,
    GridSquare,
};

enum class BattleAreaAnchorKind
{
    FixedWorldPosition,
    FollowSourceUnit,
};

struct BattleAreaGeometry
{
    BattleAreaShape shape{};
    int radiusTiles = 0;
    int squareSideTiles = 0;
};

struct BattleAreaAnchor
{
    BattleAreaAnchorKind kind{};
    Pointf fixedPosition;
    int sourceUnitId{};
};

struct BattleAreaEffect
{
    BattleAreaId id{};
    EffectSourceBinding source{};
    int sourceTeam{};
    BattleAreaGeometry geometry{};
    BattleAreaAnchor anchor{};
    int createdFrame{};
    int expiresFrameExclusive{};
    AreaSourceDeathPolicy sourceDeath{};
    AreaMergeKey mergeKey{};
    AreaMergePolicy merge{};
    std::vector<AreaModifier> modifiers;
};

struct BattleAreaEffectState
{
    int nextAreaId{};
    std::vector<BattleAreaEffect> areas;
};
```

`sourceTeam` 在建立時保存，固定區域即使來源死亡也不需解參考死者。`AreaMergeKey` 由來源 binding、規則 ID 與目標 team domain 形成，不用顯示名或幾何位置判斷「同一區域」。

## 幾何契約

### 圓形

- `radiusTiles` 必須大於 0。
- 世界半徑為 `radiusTiles × BattleGridTransform::tileWidth`。
- 單位中心與區域中心的平方距離 `<= radius²` 視為區域內；邊界包含。
- 計算使用現有 deterministic 座標型別與相同運算順序，不能在 GUI／headless 使用不同 helper。

### 棋格方形

- `squareSideTiles` 必須是正奇數，例如 5×5 填 5。
- 固定世界中心先透過共用 `BattleGridTransform` 轉成中心格；涵蓋中心格向四方各 `(side - 1) / 2` 格。
- 查詢單位以當下占用／所在格判斷，邊界格包含。
- 若世界位置剛好落在格界，使用現有 world-to-cell 規則，不另以四捨五入近似。

龍象的 5×5 是即時 `DealDamageAction`，可共用上述 `GridSquare` geometry value／查詢 helper，但不建立 `BattleAreaEffect` 或 timer。

## Anchor 與來源死亡

| anchor | 中心 | 來源死亡 |
|---|---|---|
| `FixedWorldPosition` | 建立後位置不變 | 依 payload；黃沙使用 `PersistUntilExpiry` |
| `FollowSourceUnit` | 每次查詢讀取來源當下位置 | 依 payload；伏魔使用 `RemoveImmediately` |

跟隨區域不每幀複製 center，也不在單位移動時遍歷全部區域。查詢時解析 anchor，presentation 也從同一 helper 取得中心。

來源死亡採 `RemoveImmediately` 時，在死亡 transaction 完成、死亡效果開始前移除；同一幀後續傷害與位移查詢不再看見該區域。固定黃沙保留到自然到期，team 與 modifier 仍取建立時 snapshot。

## 建立、刷新與到期

區域在 action commit 時立即加入 state：

```text
createdFrame = currentFrame
expiresFrameExclusive = currentFrame + durationFrames
active ⇔ createdFrame <= queryFrame < expiresFrameExclusive
```

因此在第 N 幀建立、持續 100 幀的區域，可影響第 N 幀建立後的結算及第 N+1…N+99 幀；第 N+100 幀開始前移除。每幀 status tick 前統一 `removeExpiredAreas(currentFrame)`，到期不依 vector erase 順序觸發 gameplay。

`AreaMergePolicy`：

| 政策 | 行為 |
|---|---|
| `Independent` | 新建 area ID，各自到期 |
| `RefreshSameSource` | 同 merge key 保留 area ID，更新 anchor／geometry／modifier，重設到期幀 |
| `ReplaceSameSource` | 先發出 removed，再建立新 area ID；只在 presentation 必須重播建立效果時使用 |

黃沙使用 `RefreshSameSource`：新命中位置成為固定中心，範圍與期限刷新，不同施法者各自持有區域。伏魔也使用 `RefreshSameSource`：跟隨同一施法者，重施只刷新期限。

## 查詢 API

```cpp
std::vector<BattleAreaRef> areasContainingUnit(
    const BattleRuntimeState& state,
    int unitId,
    AreaQueryPhase phase);

BattleAreaUnitModifiers collectAreaUnitModifiers(...);
BattleAreaAttackSpawnModifiers collectAreaAttackSpawnModifiers(...);
bool blocksForcedMovement(...);
```

回傳／合併一律按 `BattleAreaId` 遞增，不能依 hash 或來源 container 順序。query 本身不改 runtime、不產生 presentation，也不快取「目前在區域內」到單位身上；每個結算點使用當下位置做 live query。

只有當未來規則真的需要 enter／leave 事件時，才增加具名邊界事件；黃沙與伏魔不需要維護每單位 membership set。

## 黃沙萬里鞭

建立規則：主彈道命中時，以命中世界位置建立半徑 6 格、持續 100 幀的固定圓形區域。

區域修正：

1. 敵方單位的速度降低 25%，使用 live unit modifier query。
2. **只有敵方單位在生成攻擊的那一刻位於沙暴內**，該枚新攻擊才套用：`tracking = false`、彈速降低 35%、彈道壓制傷害降低 35%。
3. 判斷的是攻擊來源單位位置，不是彈道生成點或飛行中位置。
4. 已生成攻擊保存修改後的 spawn payload；來源之後離開／進入、區域到期或來源死亡都不回頭修改該攻擊。
5. 同一個 attack request 只收集一次區域修正；側翼與延遲攻擊各自在自身真正生成時查詢。

多個黃沙重疊時，`tracking=false` 為布林 OR；彈速與壓制降低採 `KeepStrongest`，不是連乘或相加。完整描述應顯示「同類沙暴效果不疊加」。

這個 spawn-time 契約特別禁止兩種簡化：飛行中的彈道進入沙暴才突然減速，以及離開沙暴後恢復已生成彈道。

## 伏魔杖法

建立規則：施放時建立以施法者為中心、半徑 5 格、持續 90 幀的跟隨圓形區域；來源死亡立即移除。

三項修正在各自真正需要的結算點 live query：

| 修正 | 查詢時點 | 判斷 |
|---|---|---|
| 陣內友軍格擋率 +25% | 傷害交易收集防守 modifier 時 | defender 當下在友方伏魔陣內 |
| 陣內友軍不被擊退 | 強制位移命令套用前 | target 當下在友方伏魔陣內；只擋擊退，不擋銀索拉近等其他方向，除非 payload 明寫 |
| 陣內敵人造成傷害 -20% | 傷害交易收集攻擊 modifier 時 | attacker 當下位於敵方伏魔陣內 |

若移動在本幀較早階段使單位進／出區域，本幀後續傷害採移動後位置。攻擊在區域外生成、來源在命中前走入區域時，傷害降低會生效，因為伏魔是 live damage query，不是 spawn-time 攻擊修正。

多個伏魔陣重疊時，格擋加成與造成傷害降低各採 `KeepStrongest`，擊退免疫採布林 OR；不因多位劉處玄疊成多份 25%／20%。

## 與 frame runner 的順序

依目前每幀順序插入明確邊界：

1. 幀開始、狀態 tick 前移除 `expiresFrameExclusive <= currentFrame` 的區域。
2. 單位移動照常完成。
3. cast commit 可建立伏魔；後續同幀 attack／damage query 立即可見。
4. attack spawn 在 request 轉成 live attack 前查黃沙 spawn modifier。
5. hit action 可建立／刷新黃沙；同一幀在它之後生成的 follow-up 可見，已先生成者不變。
6. damage transaction 開始時分別收集攻擊方／防守方 live area modifier。
7. force-move command 真正套用前查詢免疫。
8. 單位死亡時立即執行該 area 的 source-death policy。
9. presentation 在 gameplay commit 後讀取 area created／refreshed／removed events。

同一階段內依 action order 及 area ID 固定。區域 query 不使用亂數。

## Presentation、digest 與 replay

area gameplay state 納入 runtime snapshot 與 digest：ID、來源 binding、team、geometry、anchor、created／expiry frame、merge key 及 modifiers 都要序列化。跟隨區域不序列化每幀衍生 center，只序列化 source unit ID。

presentation event 僅有 `Created`、`Refreshed`、`Removed`，攜帶 semantic area kind 與 area ID；視覺動畫不能回寫 gameplay timer。GUI／headless 都執行相同 state 與 query，只是 headless 不消費 visual event。

## 測試

- 圓形中心、內部、邊界、邊界外；5×5 四角與格界轉換。
- 第 N 幀建立後立即生效、第 N+99 幀仍生效、第 N+100 幀已移除。
- 黃沙刷新移動中心且保留 area ID；兩位來源各自存在。
- 黃沙內／外生成彈道，之後進出區域不改既有彈道。
- 同幀命中建立黃沙後的 follow-up 受影響，建立前的攻擊不受影響。
- 伏魔跟隨移動、來源死亡立即移除、固定黃沙在來源死亡後保留。
- 伏魔三項 modifier 在正確 query phase 生效；拉近不被「擊退免疫」誤擋。
- 重疊採 strongest／OR，離開一區但仍在另一區時持續有效。
- area vector 以不同配置容量／erase 歷史執行，查詢順序與 digest 仍一致。
- GUI／headless、snapshot restore 與 fixed-seed replay 的區域狀態一致。
